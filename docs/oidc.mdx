---
title: OIDC identity for jobs
description: Per-org OpenID Connect issuer so jobs can assume cloud roles without stored cloud secrets.
---

Each org on a Longshore instance is its own OpenID Connect (OIDC) issuer. A running job asks for an identity token for a named audience; a cloud (AWS, GCP) or Vault that trusts the issuer exchanges the token for short-lived credentials, matching on claims such as `sub`. No long-lived cloud secret is stored in CI.

**Status.** The issuer, the mint endpoint and delivery to a job through the secrets proxy are built and tested. Tests against a cloud provider and Vault are still to do.

## Issuer

| | |
| --- | --- |
| Issuer URL | `<base>/<org slug>`, where `<base>` is `LONGSHORE_OIDC_BASE_URL`, default `<public url>/oidc` (https only) |
| Discovery | `<issuer>/.well-known/openid-configuration` |
| JWKS | `<issuer>/jwks.json` (public members only: `kty crv x y kid use alg`) |
| Signing | ES256 (P-256), supported by AWS, GCP and Vault |
| Mint | `GET` or `POST <issuer>/token?audience=<aud>` with `Authorization: Bearer <attempt credential>`; answers `{ "value": "<jwt>", "expires_at": <ms> }`, the same shape as GitHub's |

Every org has its own keys, so a key that signs for one org never signs for another. Private keys are sealed in a separate key domain from the audit key, the GitHub App and the secrets vault.

## Claims

| Claim | Meaning |
| --- | --- |
| `iss`, `aud`, `iat`, `nbf`, `exp`, `jti` | Standard. `aud` is mandatory and chosen per request (one printable string, up to 256 characters). `exp - iat` is 5 minutes; never more than 10. `jti` is unique per token. |
| `sub` | `org:<slug>:project:<slug>:repo:<owner/repo>:ref:<ref>:class:<class>:env:<env or none>`. Values the forge controls are percent-encoded, so one cannot add a `:` and forge another segment. |
| `org`, `org_id`, `project`, `project_id`, `run_id`, `job_id`, `attempt_id` | Slugs and immutable ids. Match on ids when a slug could be renamed. |
| `repository`, `repository_owner`, `ref`, `sha`, `workflow`, `workflow_ref`, `event_name`, `actor`, `environment` | Same meaning as the GitHub claims of the same name. `environment` is `null` until jobs record one. |
| `job` | The job key in the workflow. |
| `trust_class` | `protected`, `release` and so on: the class the job runs as after the demotion rule (see [Security](/security)). |

`actor` and `ref` come from the forge: use them only as extra conditions next to `sub`, never as the only check.

## Who gets a token

Only a running attempt, proven by its attempt credential (an HMAC bound to one attempt and org, expiring, in its own key domain), and only as the class the scheduler recorded for it. `untrusted_pr` and `trusted_pr` get nothing by default; `LONGSHORE_OIDC_ALLOW_CLASSES` widens that and you should not widen it to `untrusted_pr`. An unrecorded class, an attempt that is not running, a missing or malformed audience and a credential for another org are all refused. Every mint and every refusal is audited (attempt, run, job, audience, `jti`, never the token).

## How a job asks for a token

A job gets a token only when its workflow asks for one the way GitHub's does, with `permissions: id-token: write` (on the job, or on the workflow when the job has no `permissions:` block of its own; `write-all` counts). The plan records the request, so `id-token: read` or no block means no.

For such a job on an instance with the OIDC issuer and the [secrets proxy](/secrets-proxy), and a class the policy allows, the job gets two variables, as GitHub's tooling reads them:

- `ACTIONS_ID_TOKEN_REQUEST_URL`: `<issuer>/token?api-version=2.0`, the org's mint endpoint. Clients append `&audience=...`.
- `ACTIONS_ID_TOKEN_REQUEST_TOKEN`: a placeholder.

The proxy adds one rule for the job: `GET` or `POST` on exactly that path, with the real attempt credential as the bearer, made at the moment of the request and valid for two minutes. The sandbox never holds it, whatever the job sends in its own `Authorization` header is replaced, and the rest of the instance is unreachable from the sandbox. A job that did not ask, an `untrusted_pr` or `trusted_pr` job (unless you widened `LONGSHORE_OIDC_ALLOW_CLASSES`), and an instance with no issuer or no proxy get neither variable and no rule. The token itself is a short-lived JWT the job can read: keep the audience narrow, and let the cloud's trust policy match on `sub`.

## Rotation

`longshore oidc rotate --org <slug>` makes a new key current. The old key stays in the JWKS for 10 minutes (the longest a token lives) plus 5 minutes of grace, so every token it signed stays verifiable until it expires; after that it is deleted. `longshore oidc status --org <slug>` lists the published keys.

## Static hosting

To serve the JWKS from somewhere else (a bucket, a CDN), export the files and host them at the issuer URL:

```
longshore oidc export --org acme --base-url https://auth.example.com/oidc --out ./site
```

This writes `./site/acme/.well-known/openid-configuration` and `./site/acme/jwks.json`. Start the server with `LONGSHORE_OIDC_BASE_URL=https://auth.example.com/oidc` so tokens carry the matching `iss`, and re-export after each rotation.

## Trust policy examples

Use the exact `sub` of what you want to allow. Prefer matching `sub` over wildcards, and do not allow `class:untrusted_pr` or a pull request ref.

### AWS IAM

Create an OIDC identity provider with the issuer URL as the provider URL and your audience (for example `sts.amazonaws.com`) as the client id. AWS fetches the JWKS itself. Then trust it in a role:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/ci.example.com/oidc/acme" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "ci.example.com/oidc/acme:aud": "sts.amazonaws.com",
        "ci.example.com/oidc/acme:sub": "org:acme:project:web:repo:acme/web:ref:refs/heads/main:class:protected:env:none"
      }
    }
  }]
}
```

### GCP Workload Identity Federation

```
gcloud iam workload-identity-pools providers create-oidc longshore \
  --workload-identity-pool=ci --location=global \
  --issuer-uri="https://ci.example.com/oidc/acme" \
  --allowed-audiences="//iam.googleapis.com/projects/123/locations/global/workloadIdentityPools/ci/providers/longshore" \
  --attribute-mapping="google.subject=assertion.sub,attribute.class=assertion.trust_class,attribute.repo=assertion.repository" \
  --attribute-condition="assertion.trust_class == 'protected' && assertion.repository == 'acme/web'"
```

Then grant the service account `roles/iam.workloadIdentityUser` to `principalSet://iam.googleapis.com/projects/123/locations/global/workloadIdentityPools/ci/attribute.repo/acme/web`.

### Vault JWT auth

```
vault auth enable jwt
vault write auth/jwt/config oidc_discovery_url="https://ci.example.com/oidc/acme" bound_issuer="https://ci.example.com/oidc/acme"
vault write auth/jwt/role/deploy role_type=jwt user_claim=sub \
  bound_audiences=vault.example.com \
  bound_subject="org:acme:project:web:repo:acme/web:ref:refs/heads/main:class:protected:env:none" \
  token_policies=deploy token_ttl=10m
```
