</Note>

This guide takes a project from a tag to a signed release published to npm and GitHub Releases. The release lane does the signing and the publishing, from the control plane, with its own credentials. No job in your workflow holds a publish credential.

A complete example is in [`docs/examples/release.yml`](https://github.com/turntable-ci/turntable/blob/main/docs/examples/release.yml). Copy it to `.github/workflows/release.yml` and adapt it.

## Before you start

- The [release lane](/release-lane#deployment) runs as its own process (`turntable serve --roles release`), with a signing key (`turntable release init-key`) and the project pointed at it (`turntable policy set --signing-key builtin:release`).
- The project is [ingested from GitHub](/quickstart#poll-a-github-repo) and has release ref patterns (default `refs/tags/v*`; see [Signing](/signing#configuration)).
- A GitHub ruleset protects the tags (see [Releasing from a tag](/release-lane#releasing-from-a-tag)). Without one, a tag run is held until a release operator calls `approve_run`.
- You set the project variable `TURNTABLE_CI=true`, so steps gated on it are skipped: `turntable policy set --ingest on --org <slug> --project <slug> --var TURNTABLE_CI=true`. The option replaces the stored variables, so list them all.
- The lane's own settings are configured (see [Configure the lane](#configure-the-lane)).

## The release shape

1. **Create the protected tag first.** The maintainer creates it, or a prepare job running elsewhere does. The tag must match the project's release ref patterns.
2. **Build the release run from that tag.** Either the tag push is ingested (with tag patterns set by `turntable policy set --ingest on --tag-refs 'refs/tags/v*'`, the tag becomes a `release` class run), or you dispatch the workflow at the tag with `run_dispatch` (a branch or tag ref only; a tag that is a release ref gives a release run that waits for approval).
3. **Build jobs cross-compile and upload artifacts.** The artifact store records each artifact's digest.
4. **A late gate job sits in the signing environment.** It runs after the builds, with `environment: release` and `needs: [build]`.
5. **Approve the release.** The approver approves the digest of exactly the recorded artifacts.
6. **Request the release.** When the run has succeeded, call `request_release`. The lane verifies the bytes, signs, and publishes to the project's declared targets.

### Why the run is built from the tag

The lane signs only a run that meets all of these:

- It was built from `refs/tags/<tag>` (`ref_mismatch` otherwise).
- The tag, asked of the forge again by the lane, still points at the run's sha (`sha_mismatch`, `tag_not_found`).
- It already succeeded (`run_not_successful`). The signing policy checks the status before anything else about approvals.

So a run built from a branch cannot be released later by naming a tag, and a tag moved after the build is refused.

### The late gate

Put the signing environment on a job that runs after the builds:

```yaml
release-gate:
  needs: [build]
  runs-on: ubuntu-24.04
  environment: release
  steps:
    - run: echo "Release ${TAG} approved for signing"
      env:
        TAG: ${{ github.ref_name }}
```

The approval of the project's release environment is a `turntable.approve_release.v2` statement bound to `manifest_sha256`, the digest of the artifacts the server recorded. The approver sees each artifact (name, size, sha256) and the digest before signing:

```sh
turntable approvals approve-release --url https://ci.example.com --org acme --project api \
  --run <run id> --approver <approver id> --key key.pem --token-file operator.token
```

See [Approving a release](/security#approving-a-release-in-the-ui-and-with-the-cli).

<Warning>
  Do not put the signing environment on an early job. The manifest needs recorded artifacts, so a job that waits for approval before the builds finish cannot be approved: the challenge is refused for a run with no recorded artifact yet.
</Warning>

### Other environments

Any other environment (`npm`, `production`) uses the v1 approval (`longshore.approve_environment.v1`), bound to the run's sha and workflow hash. A v1 statement for the release environment is refused (`release_requires_v2`), and a v2 statement for any other environment is refused (`not_a_release_environment`).

### Request the release

```sh
curl -sS -X POST https://ci.example.com/api/v1/release-requests \
  -H "Authorization: Bearer $(cat operator.token)" -H 'content-type: application/json' \
  -d '{"run_id":"<run id>","tag":"v1.0.0","artifacts":["app-linux-x64","app-linux-arm64","app-darwin-arm64"]}'
curl -sS https://ci.example.com/api/v1/release-requests/<request id> -H "Authorization: Bearer $(cat operator.token)"
```

`request_release` and `get_release_request` need the `release_operator` role. `request_release` is not an MCP tool, and there is no CLI command for it yet. The request ends as `signed`, or as `refused` with a `reason` code from the [table below](#common-refusals).

The artifact names are the names you gave `actions/upload-artifact`. The signed subjects are the files inside each uploaded zip (see [Artifacts from jobs](/release-lane#artifacts-from-jobs)).

## Gate in-run publishing off

Steps that publish or attest from inside the run would use credentials the job should not hold. Gate them off on Turntable:

```yaml
npm-publish:
  if: vars.TURNTABLE_CI != 'true'
```

This covers `npm publish`, `gh release`, `actions/attest-build-provenance` and `--provenance`. On GitHub the variable is unset, so the same workflow still publishes there.

Turntable runs Linux sandboxes only. Gate jobs it cannot run (macOS, Windows) the same way, or keep them on another runner. A macOS job that is not gated is reported as unsupported.

If a job must publish itself, use [compat mode](#when-a-job-must-publish-itself).

## Dry run first

A release with no publish targets declared signs and records `signed`, and publishes nothing. The lane's publish step returns an empty list, a clean state. Use it to check the whole path (the tag, the approval, the bytes and the signature) before you give the lane any publish credential.

1. Make sure `turntable release publish-target list --org <slug> --project <slug>` prints nothing.
2. Tag, let the run finish, approve the gate and call `request_release`.
3. Expect `status: signed` with a `key_id`, and nothing published.
4. [Verify the statement](#verify-a-release).
5. Declare the targets and release the next tag.

The same bytes of a tag sign again only with identical digests, so a dry run on a tag does not stop you releasing that tag after you declare targets. Releasing the same tag with other bytes is refused as an attestation mismatch.

## Configure the lane

These commands act on the release lane's own file, and use the release role's environment (`TURNTABLE_RELEASE_*`):

```sh
turntable release pin-repo --org acme --project web --repo acme/web
turntable release publish-target set ...
turntable release publish-target list --org acme --project web
```

Release vault secrets are set with `turntable secret set --master-key-file <release key>`, with the release master key.

<Warning>
  These are CLI commands only. No REST or MCP operation and no instance setting does the same, and `request_release` cannot pin a repository or declare a target. A hosted instance image has no shell, so there the instance operator has to run them. Release lane configuration ops for shell-less instances are planned ([#541](https://github.com/turntable-ci/turntable/issues/541)): pin the repository, publish targets, lane secrets, create the release key. Until then this is not available for shell-less instances.
</Warning>

## Publishing to npm

The lane publishes to npm. A workflow job does not.

Declare the target, naming the tarball artifact and a vault secret:

```sh
turntable release publish-target set --org acme --project web --key npm \
  --kind npm --package @acme/web --artifact web-1.0.0.tgz --secret NPM_TOKEN \
  --accept-long-lived-token
```

- `--artifact` names a file inside an artifact the request asks for. The package name, version and tag must match the tarball; private packages are refused, and an existing version is accepted only with the same integrity.
- Optional: `--tag latest` and `--access public|restricted`.
- `--accept-long-lived-token` is required. npm trusted publishing does not accept a self-hosted issuer, so the lane holds a long-lived npm token. Make it granular, scoped to the package and publish-only.
- The token is a vault secret of the **release vault**: sealed with the release master key, usable by `release`-class jobs and by nothing else. The main process's vault refuses it (`release_lane_only`). Set it with `turntable secret set --org acme --name NPM_TOKEN --value-stdin --master-key-file <release key>`.

### Provenance

`npm publish --provenance` is dropped on Turntable. npm accepts that attestation only from GitHub's or GitLab's OIDC, so a Turntable run cannot make it. A package published by the lane has no npm provenance badge.

Consumers verify Turntable's signed statement instead. Declare a GitHub release target with the provenance asset (the default), and give consumers the release public key. They then run [`turntable verify`](#verify-a-release) on the tarball.

### When a job must publish itself

Declare the target with `--mode compat`. The job runs `npm publish` as before, behind the lane's release proxy, which supplies the credential and allows only the one package document the lane derived from the verified tarball. A package whose `package.json` `npm publish` rewrites will not match: publish it in strict mode. The rules are in [Compat mode](/release-lane#compat-mode-the-job-publishes-the-lane-holds-the-credential).

## Verify a release

The lane attaches the signed in-toto statement (a DSSE envelope) to a GitHub release as `provenance.intoto.json`, unless the target disables it. Download it and the artifact, and use the public key `turntable release init-key` printed:

```sh
turntable verify app-linux-x64 --provenance provenance.intoto.json --pubkey release.pub --name app-linux-x64
```

Exit code 0 means verified, 1 not verified, 2 a usage error or an unreadable file. It checks the signature under the key you give, that the statement is SLSA v1, and that the artifact's digest is one of its subjects. See [Signing](/signing#verifying).

`get_release_request` returns the status, the reason and the key id, not the envelope. Getting the envelope when there is no GitHub release target is not available yet.

## If your clients pin a signing key

Some projects' clients accept a release only if a file, such as a manifest, is signed by a key pinned in the client. A key held by Turntable would be rejected. There are three ways to handle that. The most direct is a [lane-verified co-signature](#co-sign-with-the-key-your-clients-pin).

### Verify on Turntable, sign externally

1. Run the release on Turntable with no publish targets, as in the [dry run](#dry-run-first). The lane signs its provenance and records `signed`, and publishes nothing.
2. The project's existing publisher downloads the artifacts and the provenance, then runs `turntable verify <artifact> --provenance <file> --pubkey <file>` against the lane's public key. Pin that key out of band, not next to the artifacts.
3. If verification passes, the publisher signs with its own pinned key and publishes.

Two parts of this path are planned. Fetching the provenance envelope from the release request is planned ([#541](https://github.com/turntable-ci/turntable/issues/541)), and so is reading the lane's public key (`release_public_key`, [#541](https://github.com/turntable-ci/turntable/issues/541)). Until then, the envelope is not available yet when there is no GitHub release target. The public key is the one `turntable release init-key` printed when the key was created; there is no other command to read it again.

### Co-sign with the key your clients pin

The key's owner signs the exact release file off-instance, with the signer they already use. The release request carries that signature. The release lane, never the main process, verifies it against a public key you configure on the lane, and publishes it next to Turntable's own provenance. The lane never holds the private key and never receives it.

**Configure the key.** Set the public key from the **Release lane** page of the web app (an owner of the operator org, with a passkey step-up) or with the operations `release_cosign_key_set`, `release_cosign_key_remove` and `release_cosign_key_list` (REST, never MCP; the same credential rule as the other lane configuration: a signed-in web session of an owner of the operator org plus a fresh step-up, and a `tti_` token, an org token or MCP is refused). Public material only; it lives in the lane's own file. The audit trail records the key's name, its id (the first 16 hex characters of SHA-256 over the SPKI DER, what a client pins) and the full SPKI fingerprint, never the key. `turntable release cosign-key set|remove|list` on the lane's host is a thin client of the same code.

```sh
turntable release cosign-key set --org acme --project web --name pinned \
  --public-key-file pinned.pub.pem --signs manifest.json --output-name manifest.json.sig \
  --manifest-binaries
turntable release cosign-key list --org acme --project web
```

| Setting | Meaning |
| --- | --- |
| `name` | A short name; the request refers to the key by it. |
| `public_key_pem` (`--public-key-file`) | The PEM public key your clients pin. A private key is refused. |
| `signs` | The file in the release whose exact bytes are signed, by its path inside the artifact, for example `manifest.json`. |
| `output_name` | The release asset name the signature is published under, for example `manifest.json.sig`. |
| `format` | The signature format. Default and only one so far: `detached-der-p256-sha256`. |
| `manifest_binaries` (`--manifest-binaries`) | The signed file is a manifest of binaries in the fixed shape below, and the key also signs every binary it lists. |

Any change to a co-signing key (set, replace or remove) moves the lane's configuration version, so a release approved before it must be approved again: the publish is refused with "release lane config changed since approval; re-approve".

Once a key is configured, every release of the project needs a valid co-signature from it. Names, signed files and output names must be unique across a project's keys. `detached-der-p256-sha256` matches clients that check an ECDSA P-256 signature over the SHA-256 of the exact file bytes, in minimal DER, one `<file>.sig` per signed file.

**The manifest shape** (the shape one pinned-key client checks): `manifest.json` is

```json
{ "version": "1.2.3",
  "signing_key_id": "0123456789abcdef",
  "binaries": { "linux-x64": { "filename": "app-1.2.3-linux-x64", "sha256": "<lowercase hex>" } } }
```

`version` is the tag's version, with or without a leading `v`; `signing_key_id` is the pinned key's id; `binaries` is a map from platform to the binary's file name and sha256.

**Files, not artifacts.** A recorded artifact is one zip per `upload-artifact` name, and the lane signs the files inside it, named by their path in the zip. For example, an artifact `release-binaries` holds the versioned binaries, `manifest.json` and `SHA256SUMS`, and an artifact `npm-package` holds the one `.tgz`. Request both artifacts.

**Sign and request.** Sign `manifest.json` and each binary file (for example `openssl dgst -sha256 -sign pinned.key -out manifest.json.sig manifest.json`), base64 each signature, and pass them. A signature over a binary names it in `file`:

```json
{ "run_id": "...", "tag": "v1.2.3", "artifacts": ["release-binaries", "npm-package"],
  "cosignatures": [
    { "name": "pinned", "signature_b64": "MEUCIQ..." },
    { "name": "pinned", "file": "app-1.2.3-linux-x64", "signature_b64": "MEQCIB..." } ] }
```

**What the lane checks, before it signs or publishes anything.** The manifest signature is verified over the exact bytes of the file, the bytes it re-hashed for the approved manifest, under the configured key, in minimal DER (a non-minimal encoding of a valid signature is rejected, because strict clients reject it). Then, for the manifest: `signing_key_id` equals the configured key's id; `version` matches the tag; and for every entry of `binaries`, `filename` is a file of the run's artifacts, its `sha256` (lowercase hex) is that file's digest, and `<filename>.sig` verifies under the key. A listed file that is missing, an unsigned binary in the manifest's artifact that the manifest does not list (only `SHA256SUMS` is allowed besides), a signature for an unlisted file, a duplicate file name and a signature asset name another file already has are all refused. A missing, invalid, wrong-key, wrong-bytes, wrong-release, duplicate or unknown co-signature means nothing is signed or published, with a reason (see the table below).

**What gets published.** Each verified signature is attached to the GitHub release as raw bytes under its output name (`manifest.json.sig`, and `<filename>.sig` per binary), next to the provenance. The request result lists each co-signature's name, key id and signature digest.

**See the status.** `get_release_request` returns `cosignatures`: each is `present` (carried, not yet checked), `verified`, `missing`, `invalid` or `unexpected`, with the key's public fingerprint only (and the `file` for a binary).

### Dry run

`request_release` with `dry_run: true` (an `operator` or `release_operator` may ask) runs every check a real request runs, in the lane, and stops before it signs: the run is finished, successful and built from `refs/tags/<tag>`, every artifact digest, the manifest and every `.sig` as above, the version against the tag, an npm tarball's own version, and that the lane holds the project's signing key. It needs no approval and spends none, signs nothing and publishes nothing, and is audited. `get_release_request` then shows status `verified` and a `plan`: the configured targets in publish order with the assets each would publish, or `none configured`. Run it before asking for approval.

### Publishing a release with both a GitHub release and npm

Set one `github-release` target with `asset_artifacts: ["release-binaries"]` (every file of that artifact is published under its own basename, a validated plain name with no collisions, plus the co-signature files; `assets` still lists single files) and one `npm` target whose `artifact` is the artifact `npm-package` (the lane takes the single `.tgz` file inside it, and refuses if there are none or several; a tarball's own file name still works). The configuration names no version, so it stays the same across releases.

The order is fixed, never the key order: the GitHub release first (a draft, every asset uploaded including the `.sig` files, published once), then npm, and only once that release is published. If the GitHub release did not publish, npm is not attempted: it is recorded as `skipped` with reason `github_release_not_published`.

### A stepping stone

A new client release pins a Turntable-held key in the client's spare (`next`) key slot. Once deployed clients trust it, Turntable signs the releases that follow.

The key type matters. Turntable's provenance signature is Ed25519. Clients that pin an ECDSA P-256 key need a P-256 signer, which is planned ([#427](https://github.com/turntable-ci/turntable/issues/427), an AWS KMS P-256 signer).

## Common refusals

A `reason` on a release request comes from the lane (`release/lane.ts`) or the signing policy (`signing/policy.ts`, reported as `signer:<reason>`). The other rows are refusals from approvals and the vault.

| Reason | What it means | What to do |
| --- | --- | --- |
| `ref_mismatch` | The run was not built from `refs/tags/<tag>`. | Dispatch or ingest the run at the tag, and request that run. |
| `sha_mismatch`, `tag_not_found` | The forge says the tag points at another commit, or does not have it. | Do not move tags. Create a new tag and a new run. |
| `signer:run_not_successful` | The run has not finished with `success`. | Wait for it, or fix and rerun. |
| `repo_not_pinned` | The project has no pinned repository. | Run `turntable release pin-repo` on the lane's host. |
| `repo_mismatch` | The run's repository is not the pinned one. | Check the pin and the project's ingested repo. |
| `signer:no_approval`, `signer:manifest_mismatch` | No approval of the release environment, or one for other artifacts. | Approve the late gate over the same artifact set you request. |
| `release_requires_v2` | A v1 approval was sent for the release environment. | Use `release_approval_challenge` and `approve_release`, or `turntable approvals approve-release`. |
| `not_a_release_environment` | A v2 release approval was sent for another environment. | Approve that environment with the v1 statement. |
| `release_lane_only` | The main process's vault was asked for a release-class secret. | Keep the secret in the release vault and do not read it in a job. |
| `signer:not_release_class`, `signer:ref_not_a_release_ref` | The run is not a release run, or its ref is not in the release ref patterns. | Check `--tag-refs` and `--release-refs`. |
| `signer:no_signing_key` | The project has no signing key. | `turntable policy set --signing-key builtin:release`. |
| `unknown_run`, `no_repo`, `bad_tag`, `no_artifacts` | The request names an unknown run, a run with no repository, an invalid tag or no artifacts. | Correct the request. |
| `artifact_not_recorded`, `signer:artifact_not_recorded` | An artifact name was never uploaded by the run. | Use the names from `actions/upload-artifact`. |
| `artifact_bytes_missing`, `digest_mismatch`, `size_mismatch` | The lane could not read the bytes, or they differ from the record. | Check `TURNTABLE_RELEASE_ARTIFACT_DIR`; rebuild. |
| `unpack_failed`, `duplicate_subject` | A zip the lane refuses to unpack, or two files with one name. | See the limits in [Artifacts from jobs](/release-lane#artifacts-from-jobs). |
| `attestation_mismatch` | The tag was attested before with other digests. | Release a new tag. |
| `cosign_missing`, `cosign_unexpected`, `cosign_duplicate`, `cosign_bad_encoding` | A configured co-signature was not carried, one names no configured key, one repeats, or one is not base64. | Send exactly one `cosignatures` entry per configured key. |
| `signature_invalid`, `signature_not_minimal_der` | The signature does not verify over the exact bytes under the configured key, or is not minimal DER. | Sign this release's file with the pinned key and emit minimal DER. |
| `cosign_artifact_missing`, `cosign_artifact_differs`, `cosign_manifest_check`, `cosign_config_error` | The signed file is not in the release, differs from the approved digest, fails the manifest check (key id, version, a binary's digest, a missing or unlisted binary), or the lane's co-signing configuration is unreadable. | Check the `signs` file is in a requested artifact, and the manifest's `signing_key_id`, `version` and `sha256` values. |
| `run_not_successful`, `no_signing_key`, `publish_plan_refused` | A dry run: the run is not `success`, the lane holds no signing key for the project, or a target could not publish (the detail names it). | Fix it, then dry-run again. |
| `frozen` | An incident freeze is on. | Unfreeze with `turntable incident unfreeze`; the request is then processed. |
