<Note>
  The signing service, the key backends, the provenance and `turntable verify` are built. The [release lane](/release-lane) records artifacts and calls the service, and it checks [human approvals](/security#human-approvals) before it signs, so the service signs nothing without them.
</Note>

Turntable's control plane signs release artifacts and writes the provenance that says how they were built. The job never holds a signing key, and the job does not write the provenance.

## What is signed

The service builds one **in-toto statement** with a [SLSA v1](https://slsa.dev/spec/v1.0/provenance) provenance predicate and signs it as a [DSSE](https://github.com/secure-systems-lab/dsse) envelope with Ed25519.

| Field | Value |
| --- | --- |
| `subject` | The artifacts being attested: name and sha256, taken from the artifact store. |
| `buildType` | `https://longshore.dev/buildtype/workflow/v1` |
| `externalParameters` | The workflow path, ref, sha, event and inputs. |
| `resolvedDependencies` | The source commit, and every action commit the run pinned (from the plans stored when its attempts started). |
| `runDetails.builder.id` | The Turntable instance. |
| `runDetails.metadata` | The run id as the invocation id, and the start and finish times. |
| `runDetails.byproducts` | The run's other recorded artifacts, by digest. |

## Guarantees

- The service signs only digests recorded in the artifact store for that run. A caller names a run and artifact names; it never supplies a digest, a class, a ref or a key.
- A recorded artifact is never changed: a name is recorded once per run, and the store has no update or delete.
- A run is signed only if its stored class is `release`, it succeeded, its ref matches the project's release ref patterns, the project has a signing key, and its environment's approval is present. Any other answer is a refusal, and refusals are audited.
- Every signature and every refusal is written to the audit log, with the key id and the digests and never key material, before the signature is returned.
- The provenance is generated by the control plane from stored facts. Nothing in it comes from the job.
- Private keys are never exported: a backend can sign and name its public key, and nothing else.
- A signature that does not verify under its own backend's public key is never returned.
- Cloud backends authenticate with short-lived credentials from the org's identity issuer. No static cloud key is stored or used.
- The signing request names a key by reference, and the reference is checked against the backend's own format before any request is made.

## Backends

A project's signing key is `<backend>:<reference>`:

| Backend | Reference | Notes |
| --- | --- | --- |
| `builtin` | A key name | An Ed25519 key sealed in the system secret domain. For self-hosters and tests. |
| `aws-kms` | A key ARN | An `ECC_NIST_P256` key; `Sign` with `ECDSA_SHA_256` over the digest, authenticated by OIDC web identity (see [AWS KMS](#aws-kms)). The envelope carries the DER signature. |
| `gcp-kms` | A full key version name | An `EC_SIGN_ED25519` key version; `asymmetricSign` with a short-lived OAuth token. |

KMS requests go through the same guarded outbound client as everything else the control plane fetches. Exchanging the org's OIDC token for those temporary credentials is the issuer's job ([#43](https://github.com/nc9/turntable/issues/43)); the backends take a function that returns them.

## AWS KMS

The `aws-kms` backend signs with a non-exportable P-256 key and holds no cloud key of its own. For each signature the release lane:

1. mints an OIDC token from the org's issuer with `sub` `turntable:release:<org>/<project>` (never a job or an attempt, so no job at any trust class can meet a trust policy pinned to it), the configured audience (default `sts.amazonaws.com`) and a life of at most 5 minutes;
2. calls `sts:AssumeRoleWithWebIdentity` for the configured role with `DurationSeconds` 900 (an unsigned call; the token is the credential);
3. calls `kms:GetPublicKey` (cached per key) and refuses the key unless its public key hashes to the pinned fingerprint (`key_mismatch`);
4. calls `kms:Sign` with `MessageType` `DIGEST` and `ECDSA_SHA_256` over the SHA-256 of the DSSE pre-authentication encoding.

The requests are signed with SigV4 by Turntable itself, with no AWS SDK. Credentials stay in memory, are reused until one minute before they expire, and are never logged or audited. The only hosts called are `sts.<region>.amazonaws.com` and `kms.<region>.amazonaws.com`, for the configured region. The audit row (`kms_sign`) records the key ARN and the digest, and on failure one of `sts_denied`, `kms_denied`, `kms_throttled`, `key_mismatch` or `network`.

### Configuration

The `aws_kms_keys` org setting maps a key ARN to its access, in the environment (`TURNTABLE_AWS_KMS_KEYS`, JSON) or `turntable.toml`. It holds no secret:

```toml
[orgs.acme.signing.aws_kms_keys."arn:aws:kms:us-east-1:111122223333:key/0123abcd-0123-4abc-8def-0123456789ab"]
role_arn = "arn:aws:iam::111122223333:role/turntable-release"
region = "us-east-1"
audience = "sts.amazonaws.com"
public_key_fingerprint = "<hex sha256 of the key's SPKI DER>"
```

Take the fingerprint from the key you created: `aws kms get-public-key --key-id <arn> --query PublicKey --output text | base64 -d | sha256sum`. Then set the project's key with `turntable policy set --signing-key aws-kms:<arn>`. If the project restricts OIDC audiences, allow the audience there too.

### AWS setup

Register the IAM OIDC provider for `<public url>/oidc/<org>` only after the final domain is live: the issuer URL is part of the trust and changes with the public URL. Use the audience as the client id.

Trust policy of the role, pinned to the release subject and the audience:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/ci.example.com/oidc/acme" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "ci.example.com/oidc/acme:sub": "turntable:release:acme/app",
        "ci.example.com/oidc/acme:aud": "sts.amazonaws.com"
      }
    }
  }]
}
```

Key policy: the role may `kms:Sign` and `kms:GetPublicKey` and nothing else; a separate admin role manages the key and cannot sign; deletion has a 30-day window (`PendingWindowInDays` 30); CloudTrail records every `Sign`.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "Admin", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/kms-admin" },
      "Action": ["kms:Create*", "kms:Describe*", "kms:Enable*", "kms:List*", "kms:Put*", "kms:Update*",
                 "kms:Revoke*", "kms:Disable*", "kms:Get*", "kms:Delete*", "kms:TagResource",
                 "kms:UntagResource", "kms:ScheduleKeyDeletion", "kms:CancelKeyDeletion"],
      "Resource": "*" },
    { "Sid": "Sign", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/turntable-release" },
      "Action": ["kms:Sign", "kms:GetPublicKey"], "Resource": "*" }
  ]
}
```

### Rotation

The KMS key is a day-to-day release key under an offline root: the root signs a delegation to the key's public key, and verifiers trust the root. To rotate, create a new key, have the root delegate to it, add its ARN and fingerprint to `aws_kms_keys`, point the project at it, then disable and schedule deletion of the old key. A key re-created under the same ARN is refused by the pinned fingerprint until an operator changes it.

## Configuration

```sh
turntable policy set --signing-key builtin:release --org <slug> [--project <slug>]
turntable policy set --release-refs 'refs/tags/v*,refs/heads/release/*' --org <slug> [--project <slug>]
turntable policy show --org <slug>
```

The approval environment defaults to `release` and is set with `--signing-environment <name>`. It is the project's own setting: `sign_release` takes no environment from the caller, refuses a request that names a different one, asks for approval in the project's environment, and records it in the provenance (`internalParameters.environment`) and the audit row.

A `builtin:<name>` key is looked up inside the org that owns the run (the org id is part of the stored name), so a project cannot name another org's key, and the same name in two orgs is two keys. A key outside Turntable (`aws-kms:`, `gcp-kms:`) may belong to one org only: `policy set` refuses a reference another org already uses, and signing is refused with `key_shared` if two orgs come to name the same one. Keys made before this change were stored under the bare name; create them again with `release init-key --org` and pin the new public key.

Release refs default to `refs/tags/v*`. An empty `--signing-key ''` unsets the key, and a project with no key cannot sign. Both are changed from the CLI only.

## Verifying

```sh
turntable verify <artifact> --provenance <file> --pubkey <file> [--name <subject>]
```

It hashes the artifact, checks that the DSSE signature verifies under the public key you give it (an Ed25519 SPKI PEM), that the envelope carries an in-toto statement with a SLSA v1 predicate, and that the artifact's digest is one of the statement's subjects (and its name, with `--name`). It trusts only that key. Exit code 0 means verified, 1 not verified, 2 usage or an unreadable file.

The public key of a built-in key is available from the service; a KMS key's public key is the one its console or API reports.

## Limits

- The service has no upload path of its own: it reads artifacts from the store through the repos, which the [release lane](/release-lane) fills.
- Only Ed25519 is supported.
- Vault Transit is not a backend yet; the interface is the same.
