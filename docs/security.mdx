</Warning>

The goal is one instance that safely runs PR CI, website publishing and signed releases, with no second instance needed.

## Secrets vault

Secrets live in a vault with pluggable stores and scopes, so a secret is available only to the org, project, environment or job that needs it. Issue [#14](https://github.com/nc9/turntable/issues/14).

## Secrets proxy

Sandboxes never hold raw secrets. A proxy sits on the sandbox's network path and injects credentials into outbound requests, per allowed host. Job code and third-party actions see placeholders at most. Issue [#15](https://github.com/nc9/turntable/issues/15).

## Egress lockdown

Sandboxes get an egress policy: outbound traffic is denied by default and allowed per host. This backs the proxy, because a secret can be injected only toward hosts the policy allows. Issue [#16](https://github.com/nc9/turntable/issues/16).

## Trust classes and fork PR gating

Every run the server ingests gets a trust class, decided once at ingest from forge facts that are re-fetched then (never taken from pull request text), and stored on the run with those facts and the reasons, so an audit or the UI can show why. `get_run` returns it as `trust`.

| Class | Meaning | Secrets and write token |
| --- | --- | --- |
| `protected` | a push to a protected ref, a schedule, or a maintainer's manual run on one | allowed |
| `release` | a release tag, or a maintainer's manual run on one | allowed |
| `trusted_pr` | a same-repo pull request whose opener can write, a push to another branch, a writer's manual run | never |
| `untrusted_pr` | everything else: a fork, an author who cannot write, an author whose permission could not be read | never |

**Facts.** A pull request is trusted only if its head repo is the base repo (a fork is untrusted whatever its author's standing) and its opener has write, maintain or admin permission, read from `GET /repos/{owner}/{repo}/collaborators/{user}/permission` with the poller's token. The forge is not asked about a fork's author. If the token cannot ask (401, 403), the author is untrusted and the decision records `permission: unknown`; a rate limit or server error fails the poll, which retries, rather than deciding on a guess. `authors` in the poll config is an explicit trusted list that works without asking the forge, for same-repo pull requests only. Protected refs are the default branch, the project's `protectedRefs`, and any branch the forge reports as protected.

**Waiting for a human.** A run classified `untrusted_pr` is created but every job waits in `awaiting_approval`, in the same transaction that creates it, so nothing can start. With `prMode: allowlist` nothing is held: only same-repo pull requests by listed authors run, and every other pull request is refused without a run. With `prMode: approval` every open pull request is ingested and untrusted ones are held. At most `maxWaitingRuns` (default 20) runs of a repo wait at once (a new push to a waiting pull request replaces it, so it is not blocked by the cap), and held runs do not count toward `maxRunsPerHour`, and neither do pull request markers that are untrusted or not yet classified, so strangers cannot use up the default branch's runs. Work on strangers' pull requests is bounded before any forge call is spent on it: the waiting cap is checked first, at most `maxNewPrsPerPoll` (default 5) pull requests from authors outside `authors` are examined per poll (the rest wait for the next poll), and a pull request skipped because the queue is full is remembered by head sha until room opens up.

**Approval.** `approve_run` releases a held run. It needs the `release_operator` role by default; an org can lower that to `operator` with `longshore policy set approve-run-min-role operator --org <slug>` (`longshore policy show` reads it, and the change is audited). **The risk of lowering it:** an operator token may belong to an agent that has just read the untrusted pull request's title, body and diff, so a prompt injection in that text could get the agent to approve its own attacker's code. The sandbox still has no secrets, but it does run the code. Keep `release_operator`, and have a person approve, unless you accept that. The caller passes the run's `head_sha` and the `workflow_hash` shown by `get_run`; both must equal what the run was decided on, or the call is refused with 409. Approving means "I read this commit and this workflow." A new push to the pull request is a new run with its own hold and its own approval, and the older waiting run of that pull request is cancelled. Approval never raises the class: an approved fork run still gets no secrets and no write token, and the class on the run is not changed. The worker checks the same binding again before starting an untrusted run: no approval, a different sha, or a workflow file whose hash differs from the approved one ends the job as `infra_error`. **Labels and comments are never read**, so no label can approve a run.

**Egress.** Untrusted code with network access is a mining and exfiltration vector even without secrets, so a run classified `untrusted_pr` gets egress `none` whatever the repo or project allows. A repo's poll config may set `untrustedEgress: "allowlist"`; `open` is not accepted. The worker applies the same cap to the run's plan, so a plan that says otherwise is still held at `none`.

**Isolation fails closed.** A run is trusted for isolation only when its stored class is `protected`, `release` or `trusted_pr`, or it is a local run (`longshore run`, from your own checkout). A missing, unknown or unparseable class is untrusted, as is a job that needed approval or that the privileged-trigger rule demotes (including a job whose own step checks out the PR head, listed at ingest).

**Concurrency.** A held run's workflow file chooses its own `concurrency` group, so its group is rewritten to one scoped to its pull request (`untrusted:pr-<n>:<group>`). Runs record their repo, and pull request numbers, concurrency groups and caps are all scoped by it, because a project can bind several repos. It can neither cancel nor block a run of the default branch.

**Manual runs.** A `workflow_dispatch` run is `protected` or `release` only when the person who started it is a maintainer (maintain or admin); a writer's is `trusted_pr`, and anyone else's, or an unknown actor's, is `untrusted_pr`, whatever the ref. Manual dispatch is not ingested yet; the rule is in the classifier.

Issue [#17](https://github.com/nc9/turntable/issues/17).

## Workflow source and workspace taint

Two questions decide whether a run can be hijacked: whose workflow file does it run, and whose code does it check out? Longshore answers both from the event, never from the payload alone, and enforces the answer structurally.

### Which ref the workflow definition comes from

| Event | Workflow definition from | Class |
| --- | --- | --- |
| `push` to a protected branch | the pushed commit (the protected ref itself) | protected |
| `push` of a release tag | the tagged commit | release |
| `push` to any other branch | the pushed commit (a push needs write access) | trusted |
| `pull_request` | the PR head, like GitHub's own event | untrusted unless a same-repo, trusted author |
| `pull_request_target`, `workflow_run`, `issue_comment`, `issues`, review and discussion events | the BASE branch (the default branch), never the head that triggered it | untrusted unless proven otherwise, and demoted when handed a non-protected ref |
| `schedule` | the default branch | protected |
| `workflow_dispatch` | the dispatched ref | by who started it: maintainer protected or release, writer trusted, else untrusted |
| `merge_group` | the merge queue commit | trusted |

Protected branches are the default branch plus the project's `protectedRefs`; release tags default to `v*`. Anything not positively trusted is untrusted: an unknown event, an unknown author, an unknown fork status.

### Credentials follow the class

Only protected and release runs may be given secrets or a token that can write to the forge. Trusted and untrusted classes never get either. This holds whatever the workflow says: a workflow cannot ask for more than its class allows.

### The demotion rule

A job on a privileged trigger (`pull_request_target`, `workflow_run`, `issue_comment`, `issues`, `pull_request_review`, `pull_request_review_comment`, `discussion`, `discussion_comment`) that **receives a non-protected ref** is demoted to untrusted **before it starts**. It receives one in two ways:

- the delivered workspace is at a non-protected ref (for example `refs/pull/9/head`), or
- one of its own steps asks for the PR head: a `with.ref` or `with.repository` that names `github.event.pull_request.head.*`, `github.head_ref`, `github.event.workflow_run.head_*`, or a `refs/pull/` ref (the classic "pwn request": check out the PR head, then run its code with the base repo's secrets).

Demotion is a property of the plan, so it happens before any sandbox exists. A same-repo author with a trusted history does not escape it.

### Lint

Two findings are lint:

- **Outside text in a script.** A `${{ }}` that reads attacker-controlled data (`github.head_ref`, PR and issue titles and bodies, comment and review bodies, branch labels and refs, commit messages and author names) inside a `run:` block or a `with.script:`. The safe form passes the value through `env:` and reads it as a shell variable.
- **A privileged job taking the PR head**, as above.

For **protected and release** runs a finding fails planning with the list of findings. For trusted and untrusted runs it is a warning. Fix it by moving the expression into `env:`, or by not checking out the head.

### No job-initiated forge fetches

The workspace is a tarball the controller delivered at one sha. The checkout stand-in only copies it and never touches the network, and a sandbox has no network unless an operator opts in. A job therefore cannot fetch a different ref, a fork, or the PR head on its own. Remote actions are fetched by sha by the controller, not the job.

## Action pins and moved tags

Before a run starts, every `uses:` reference is resolved to a commit sha, and the action is fetched by that sha. Longshore also remembers, per project, every tag-to-sha resolution it has made (`action_pins`: repository, ref, sha, first and last seen).

If a tag later resolves to a different commit, it has moved. The pin does not change on its own. A protected or release run fails with an error that names the action and both shas, until an operator accepts the move. A pull request run only gets a warning and keeps using the old pinned commit. An operator reviews the new commit (`get_action_pins` shows it as `pending_sha`), then calls `accept_action_move` with that exact sha. The call needs the operator role and is audited, and a wrong sha is refused, so accepting never blesses a commit nobody looked at. Until trust classes land, a push counts as protected and every other event as a pull request class.

### Impostor commits and nested actions

GitHub serves commits from a repository's whole fork network under the parent's name, so `uses: owner/repo@<sha>` can name a commit that exists only in an attacker's fork. Every sha, given or resolved from a tag, must therefore be reachable from a branch or tag of the named repository itself (the compare API against the default branch, then its tags and branches). An unreachable sha is refused with an error that says it may exist only in a fork. Resolving a tag to a sha and checking a sha both call the GitHub API, so the worker authenticates them with the run's own credential: the poll config's token file for a repo the poller watches, else an App installation token minted read-only for that one repo (`contents: read`), else `LONGSHORE_GITHUB_TOKEN`. The poll token serves only a run whose org and project are the ones the poll entry lands runs in. The credential is used only for the run's own repository and for actions whose owner is on the org's action-owner allowlist; it is never used for any other action (including `LONGSHORE_GITHUB_TOKEN`), and never for an untrusted run, not even for its own repo. A workflow can name any repository, so a token used for one would prove a private repo exists, reveal its shas and let a job read its code; every other action is resolved anonymously, where a private repo simply looks not found, and a private repo of an allowlisted owner is refused as a policy failure. A private repo and one that does not exist are refused with the same words (`action not available: owner/repo`), so a workflow cannot learn which private repositories exist. A local run (`longshore run`) is the operator's own checkout and token: its `LONGSHORE_GITHUB_TOKEN` is used for any action that passes the same public check, even when the run simulates a pull request. That check fails closed: only a 200 that says `private: false` passes, a 404 is not-found, and a 401, 403, 5xx or unreadable answer is an infrastructure error, never a pass. The credential and privacy decision sits outside the verdict cache, so a cache hit cannot skip it, and verdicts learned with a token are stored apart from anonymous ones and never served to an anonymous or untrusted path. Action tarballs are fetched anonymously too. Only when no credential applies are the calls unauthenticated, which share GitHub's 60-per-hour limit; the server logs once that no credential exists. Answers are kept in the database per project: a resolved tag for 5 minutes (refs move), a reachable sha for 24 hours, and an unreachable one for 10 minutes. A restart or a second job in parallel therefore asks GitHub nothing it already knows. Failures are never kept. On a rate limit (a 429, or a 403 with `retry-after` or an exhausted `x-ratelimit-remaining`) the worker waits as GitHub asks, up to 2 minutes in total per job, then retries; past that the job ends as an infrastructure error that says when the limit resets. If GitHub cannot be reached, the plan is retried; it is never treated as reachable.

Remote composite actions can contain `uses:` of their own, which act would otherwise fetch by tag over the network. So after pinning, each remote action is read at its sha. A composite's nested actions go through the same resolution: pinned by sha, checked for reachability, the owner allowlist and moved tags, and delivered locally, down to five levels. A composite whose nested actions cannot all be resolved, a docker action (top-level or nested), or a chain deeper than five levels refuses the plan. `require_sha_pins` is about what the project writes; nested tags in someone else's action do not trip it, because Longshore pins them.

### Policy rejections are failures, not infrastructure errors

A moved tag, a refused owner, an unpinned or unreachable action and the other deterministic plan rejections end the job as `failure` with the reason `policy: <message>`. They are not retried: the user can act on them. `infra_error` is kept for transient causes only (GitHub unreachable or rate limited while resolving, a provider down), which are retried.

Two optional project policies tighten this further. `require_sha_pins` refuses any `uses:` that is not already a full commit sha. The org's action owner allowlist refuses actions from any owner not on it (`longshore policy set --allow-owners actions,oven-sh`). Both are off by default and apply to nested actions inside local composite actions too.

## Outbound requests from the control plane

Everything the control plane fetches (the GitHub API and codeload, the Daytona API, release downloads, outbound webhooks later) goes through one client, `@longshore/net`. A source-guard test fails if any other code calls `fetch` or opens a connection itself.

- **Addresses.** The client resolves the host itself and requires every answer to be public. It refuses loopback, link-local (including the cloud metadata address 169.254.169.254), private RFC1918, carrier-grade NAT, unique local (ULA) and the other reserved ranges, and judges IPv6 forms that embed an IPv4 address (mapped, NAT64, 6to4) by the IPv4 address inside. Decimal and hex IPv4 spellings are normalised first. One private record among public ones is enough to refuse.
- **Pinned resolution.** The connection goes to the address that was validated. DNS is not consulted again, so a name that changes between the check and the connect (DNS rebinding) cannot redirect it. When a name has several addresses (all of them validated first), they are tried one at a time with the IPv4 and IPv6 families interleaved, each pinned to its own address, so a host with an IPv6 answer and no IPv6 route still connects over IPv4. Only a failure to connect moves on to the next address (a request that was sent is never repeated), and the overall deadline bounds all attempts together.
- **Redirects.** Followed by hand, at most 5, each hop validated in full (scheme, host, address). A redirect to a refused address is never followed, and credentials are dropped when the origin changes.
- **Scheme and URL.** https only. Credentials in the URL are refused.
- **Caps.** Responses are capped while streaming (32 MiB by default, larger for release and source tarballs) and the whole exchange, redirects included, has a 30 second deadline by default.
- **Allowlist.** `LONGSHORE_NET_ALLOW_HOSTS` names hosts that may be private and may use http, such as a local Daytona. Only those exact hosts.

An address the guard refuses ends the job as a `policy:` failure, not an infrastructure error.

## Secrets vault

Scoped, versioned secrets with policy evaluated by the core: bound to an org (and optionally a project, environment and ref pattern), usable only by the trust classes named (never `untrusted_pr`) and only toward named destination hosts. Values are sealed under a per-domain key derived from the master key, are never returned by any operation, and every use and denial is audited with the run, job, attempt and destination. Child processes the server starts get an allowlisted environment only. Delivery to jobs comes with the secrets proxy (#15). Design and threat model: [Secrets vault](/secrets-vault).

## OIDC identity for jobs

Each org is its own OpenID Connect issuer (`<public url>/oidc/<org slug>`), so a job can prove who it is to a cloud or to Vault and receive short-lived credentials, with no long-lived cloud secret in CI. Tokens are signed ES256 by per-org keys sealed in their own key domain, last at most 5 minutes, carry a mandatory per-request audience, are never issued to `untrusted_pr` (or `trusted_pr`) by default, and every mint is audited. See [OIDC](/oidc).

## Audit log integrity and export

Every write, denied write, authentication failure, policy change, token create and revoke, approval, secret change and GitHub App change is recorded. A test walks the op registry and fails if any write op does not audit.

- **Hash chain.** Each org has its own chain. An entry carries its position (`seq`), the hash of the entry before it and its own hash: sha256 over the previous hash and the canonical JSON of the entry. Editing, deleting or inserting a row breaks every hash after it. Entries written before the chain existed stay readable and are not chained.
- **Signed checkpoints.** Every 100 entries or 10 minutes (whichever comes first, only when something changed) the server signs the chain head with an ed25519 key. The key is the secret `audit/signing-key` in the encrypted secret store, which uses a different master key from the database. Each checkpoint carries the key id. The server generates the key only while the org has never signed a checkpoint. After that, a missing key is an error and an `audit_signing_key` alert entry, never a reason to make a new key: a new key would let someone who deleted the old one re-sign a rewritten chain.
- **Anchors outside the database.** Everything above lives where an attacker with database and store access can rewrite it, so verification needs two things kept elsewhere. Run `longshore audit export-key --org <slug> --out <file>` once and keep the file off the server. Ship the export sink's files off the server too: they hold every checkpoint. Then `longshore audit verify --pubkey <file> --anchor <exported file>` rejects checkpoints signed by any other key, fails if the chain lacks a checkpoint the anchor has, and fails if the database has fewer checkpoints than the anchor shows. Without them verify prints `unanchored: integrity only`: it still catches edits and deletions by anyone who cannot re-sign, but not a full rewrite by someone who can.
- **Verify.** `longshore audit verify [--org <slug>] [--pubkey <file>] [--anchor <file>]` walks every chain and exits 1 on any problem, including entries older than twice the checkpoint interval that no checkpoint covers (checkpoints deleted or signing stopped). `longshore audit checkpoint` signs the head on demand.
- **Authentication failures** are audited in the token's org when the token is known (revoked or expired), and in a system org called `_system` otherwise. Throttling is per org, failure kind and source (a token id, a hashed unknown token or a client address), at 5 per minute per source, so one noisy source cannot hide another's failures; a per-chain ceiling of 300 a minute bounds many sources. The first failure of each distinct token id is always recorded, and a dropped count rides on the next entry. Webhook requests the rate limiter already refuses are recorded only in aggregate: one entry per minute with a count.
- **Secrets** are audited by name only, never by value.
- **Export.** Entries and checkpoints stream to a JSONL directory (rotated at 10 MiB, files mode 0600) or a webhook, with at-least-once delivery and a cursor per sink that moves only after the sink accepted the batch. Webhook posts go through the outbound client and carry an HMAC in `x-longshore-signature`. Ship the files off the host to make deletion on the server detectable. `longshore audit export` runs one pass by hand.

## Scoped per-job GitHub token

Each job gets a short-lived GitHub token limited to its repository and the permissions its workflow declares. Issue [#18](https://github.com/nc9/turntable/issues/18).

## OIDC issuer

Longshore acts as an OIDC issuer so jobs can authenticate to cloud providers without stored keys. It replaces GitHub OIDC claims. npm trusted publishing does not accept self-hosted issuers, so npm uses proxy-injected tokens.

## Signing service

A signing service signs release artifacts and emits provenance, so signing keys never enter a sandbox. It is the planned substitute for GitHub artifact attestations.
