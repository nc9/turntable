Turntable talks to GitHub as a GitHub App. This page covers creating the App, where its credentials live, and how webhooks are verified. It can report each job as a check run, off by default, see [Quickstart](/quickstart#report-results-to-github-as-check-runs).

## 1. Create a master key

The App's private key, webhook secret and client secret are kept in a built-in encrypted store. Each secret is sealed with AES-256-GCM under its own data key, and the data key is wrapped by a master key from a 32-byte file.

```sh
turntable keys init --file /secure/path/master.key
export TURNTABLE_MASTER_KEY_FILE=/secure/path/master.key
```

The file is created with mode `0600` and is never printed. Back it up: without it the stored secrets cannot be decrypted. A wrong or damaged key makes decryption fail closed. Each record binds the org id and secret name into its encryption, so a stored value cannot be moved to another name or org. No operation returns a secret value.

## 2. Create the App

```sh
turntable github-app create --url https://ci.example.com [--org my-github-org] [--name Turntable]
```

This serves a local page on `127.0.0.1` and prints its address. Open it, press the button, and approve the App on GitHub (under your account, or under `--org`). GitHub redirects back to the loopback callback with a one-time code, which Turntable exchanges for the App's credentials. They go straight into the encrypted store and are not printed.

The manifest asks for the permissions below. Several are reserved for features that are not built yet; they are listed so an owner accepts them once. Not requested: workflows, administration write, secrets and webhooks.

| Permission | Level | Why |
| --- | --- | --- |
| Actions | read | Reserved for reading GitHub's own workflow runs and artifacts. |
| Actions variables | read | Reserved for reading repository variables (`vars.*`) for workflows. |
| Administration | read | Reserved for reading repository settings such as branch protection. |
| Attestations | write | Reserved for publishing build provenance attestations. |
| Checks | write | Reporting results as check runs. |
| Contents | write | Fetching the commit to run (read, today's only use). Write is reserved for job tokens of workflows that push; a job token is capped to what the workflow declares, the trust class allows and the installation has accepted. |
| Deployments | write | Reserved for deployment statuses. |
| Emails (account) | read | Reserved for matching a sign-in to a verified email. |
| Environments | read | Reserved for reading environment protection rules. |
| Issues | write | Reserved for job tokens that comment on or label issues. |
| Members (organization) | read | Reserved for checking organization membership for approvals. |
| Merge queues | read | Reserved for merge queue awareness; `merge_group` events already wake the poller. |
| Metadata | read | Listing the repositories an installation can access. |
| Organization actions variables | read | Reserved for organization-level `vars.*`. |
| Packages | write | Reserved for job tokens that publish packages. |
| Pages | write | Reserved for job tokens that deploy to Pages. |
| Pull requests | write | Reading pull request facts for polling. Write is reserved for job tokens that comment on pull requests. |
| Security events | write | Reserved for job tokens that upload code scanning results. |
| Statuses | write | Reserved for commit statuses from job tokens. |

Subscribed events are `check_run`, `check_suite`, `create`, `delete`, `issue_comment`, `membership`, `merge_group`, `organization`, `pull_request`, `pull_request_review`, `push`, `repository`, `repository_ruleset`, `workflow_dispatch` and `workflow_run`. Today `push`, `pull_request` and `merge_group` wake ingest, and an installation or repository rename re-syncs the installation; the others are recorded as `ignored` deliveries. GitHub also sends `installation` and `installation_repositories` to every App without a subscription.

### Accepting new permissions on an existing installation

An installation keeps the permissions its owner accepted until the owner accepts the App's new set on GitHub (the App's installation page shows a review request). Until then, Turntable still polls, fetches and reports checks with what was accepted. A token request that needs a permission the installation has not accepted fails with `the installation has not accepted <permission>: an owner must accept the App's new permissions on GitHub`, instead of an opaque HTTP 422. `instance_github_app_status` lists each installation as on the current set or pending acceptance, with the missing permissions. The `installation` event `new_permissions_accepted` re-syncs the installation, which refreshes the stored set.

Webhook deliveries are kept for 14 days or 50,000 rows, whichever is smaller; deliveries still waiting for their handler are never dropped.

The webhook URL is `<url>/api/v1/webhooks/github`. The `--turntable-org` flag chooses which Turntable org owns the App and its installations (default `local`).

The App is created private, so only the account that owns it can install it. To let other accounts install it (the [claim flow](/hosted#one-instance-several-orgs-claiming-an-installation)), open the App's settings on GitHub, go to **Advanced**, and choose **Make public**. The instance-hosted manifest flow does this for you when `TURNTABLE_CLAIM_INSTALLATIONS=1`.

Install the App on the repositories you want from the link the command prints.

## Installations, orgs and projects

When GitHub reports an installation, Turntable does not trust the payload. It re-fetches the installation and its repositories from the GitHub API with the App's own credentials, checks that the installation belongs to this App, and then maps it to the owning org. Which repositories it can reach is a permission, not a list of projects: the sync records the installation and creates **no project and no binding** for a repository nobody added. A payload that names a different installation, account or repository than the API reports changes nothing. A repository already bound by another installation or org is left alone and reported. Removing a repository from an installation, or uninstalling the App, unbinds it.

### Adding and removing repositories

A repository becomes a project only through an explicit step:

- `add_project {installation_id, repo, project?}` (REST `POST /api/v1/projects`, also an MCP tool) makes one repository the installation can reach a project and binds it. `repo` is `owner/name`; `project` is the new slug (default: the repo name). It asks GitHub, through the installation, that the repo is reachable and refuses one that is not. A repo that is already this org's project comes back with `created: false`; one that belongs to another org is refused. The new project has every setting at its default: no ingest and no checks, so nothing runs until it is set up. Needs owner or admin.
- The web app's **Add repositories** page (under the org's navigation) lists the repositories the installation can reach and the org has not added, with an **Add** button each. The onboarding wizard's repository step calls the same code: `onboard_repos` adds a ticked repository first, then applies the onboarding defaults. `list_installation_repos` is the source of both lists; a repository with `status: new` is one the org has not added.
- `remove_project` (REST `POST /api/v1/remove-project`, also an MCP tool) takes the project in the `project` field. It unbinds the repository and **keeps the project, its runs and its settings**; the project settings page has the same action. A later `add_project` of the repo brings the same project back. With `delete_history: true` it deletes the project and all its history (runs, jobs, logs, artifacts, and the tokens, secrets and settings scoped to it). That needs the org owner and, from the web, a fresh passkey step-up for exactly that request (`session_step_up_challenge` with action `remove_project`); a token can never delete history. The audit entry records the slug and repos.

A project whose repo was unbound because the installation lost access, or because it was removed, is listed with `no_access: true` and shows "No repository access" on the org page.

Every project has a derived `setup` state. `active`: someone added it (`add_project`), ingest is on, a static poll entry names it, or it has a run. `available` is only what an older sync made before adding was a separate step and nobody set up; `list_projects` hides those unless `include_available: true`, and the instance operator can remove them with `instance_prune_unconfigured_projects` (see [Instance administration](/instance-admin)). The flag has no other use now.

### Re-granting a repo

When an installation drops a repo (or is deleted), the sync unbinds it and records on the project which forge repo id it lost and when (`last_forge_repo_id`, `unbound_at`). The project, its settings and its runs stay. If the same forge repo id is granted again, the sync re-attaches it to that project (only a project that was added, or already had runs, is re-attached; the sync never creates one), clears the two columns and writes a `reattach_repo_binding` audit entry. Three rules hold: the project must be in the same org as the installation, the forge repo id must match (never the name alone, so a recreated repo gets a new project; a renamed or transferred one is followed, see below), and the project must have no binding now. With several candidates, the most recently unbound wins. The decision reads only these columns, never the audit log. Projects unbound before this existed have no columns set and are not re-attached. A project removed with `remove_project` forgets the lost id, so a sync never binds it back; only an explicit `add_project` does.

### Moving a polled repo to the App

A repo that was ingested by polling before the App was installed is bound with no installation, so no check runs can be posted for it. When the App is installed on it, the sync adopts that binding: it sets the installation (and the GitHub repo id, when the binding had none) and the binding keeps its project, so run history stays together. The adoption is audited as `adopt_repo_binding`. Only a binding in the same org with no installation is adopted. A binding in another org, from another installation, or whose stored GitHub repo id differs from the installation's (a renamed or recreated repo) is a conflict and is left alone. After adoption the binding is an installation binding like any other: removing the repo from the installation unbinds it, and a poll entry that still names it binds it again on the next poll cycle, into the same project: the project, its settings and its run history are kept, and the binding has no installation until the App is installed on it again.

An installation that was synced before this adoption existed has its polled repos skipped, with the binding left without an installation. Two things pick those up:

- **Boot sweep.** After the server is listening, it re-runs the sync for each active installation whose org still has a binding with no installation. It does not delay startup or `/healthz`, it makes no GitHub call when no org has such a binding, and running it again changes nothing. Failures are logged and audited as `adopt_sweep`.
- **`resync_installation`.** An org-level token with `release_operator` or higher re-syncs one installation id its org owns (`POST /api/v1/github/installations/{installation_id}/resync`, also an MCP tool) and gets back what was bound, adopted, unbound or left alone. Another org's installation id is `not_found`. It is limited to 6 calls a minute per org and then refused with `rate_limited`. Every call is audited.

### Renamed or transferred repos

A repo keeps its GitHub repo id when it is renamed or transferred. When a sync (an installation sync, an `installation_repositories` event, or a `repository` `renamed` or `transferred` event) sees a repo id that already has a binding in the same Turntable org under another slug or installation, the binding is updated in place: new owner and name, new installation. The project keeps its id, settings, runs and history, and the sync writes a `follow_repo_binding` audit entry. The installation that lost the repo does not unbind it: its removal event or sync no longer lists a binding that moved. For a transfer, claim the new owner's installation into the same org as the old one.

A binding in a different org is never moved by a sync, because that would let one tenant take another's project by installing the App on a transferred repo. The sync refuses, records a `follow_repo_binding` audit entry with the outcome `error:other_org` in the org that holds the binding, and the instance admin can still move it with `move_repo_binding`. A repo with another id under the old name never inherits the binding.

A static poll entry follows the binding of its own org and project. If the entry says `A/x` and its project's binding now says `B/x` with the same repo id, the poller polls `B/x` with the new installation's token and does not report `stale_binding`. `instance_ingest_status` shows `effective_repo` and the warning "update the poll entry's repo to B/x". Update the entry's `repo` to the new slug at your next restart or config change; until then the entry keeps working.

## Webhook verification

The endpoint, `POST /api/v1/webhooks/github`, requires `TURNTABLE_MASTER_KEY_FILE`.

- The body is capped at 25 MiB (GitHub's maximum), by `Content-Length` and by the streamed size.
- The `X-Hub-Signature-256` HMAC-SHA256 is checked over the raw body with a constant-time compare, before anything is parsed. A bad signature gets `401` and stores nothing. Repeated failures from one client are rate limited (`429`), keyed on the real client address (see `TURNTABLE_TRUSTED_PROXIES` in [Hosted deployment](/hosted)).
- The delivery GUID is stored before the `202`. A delivery with a GUID seen before is acknowledged and not run again. Deliveries are kept for 30 days.
- Events with no handler are stored as ignored and acknowledged. `push` and `pull_request` are ignored too, except that they wake the poller for the repo they name (see [Hosted deployment](/hosted)). A delivery interrupted before it finished is retried on the next start.
- Handlers are idempotent.

## Rotating the webhook secret

```sh
turntable github-app rotate-webhook-secret
```
A new secret is generated and set on the App through the GitHub API. The old one stays valid for 24 hours so in-flight deliveries still verify. If GitHub refuses the change, nothing changes locally.

## Rotating without a shell

On a hosted instance with no shell, a signed-in **owner of the operator org** (the org that owns the App) does both from the web UI, under the org's settings, App secrets. Each needs a fresh passkey step-up, enrolled in that org, for exactly that request. An instance token, an org token, a non-owner and an owner of any other org are refused. The REST ops are `instance_rotate_webhook_secret` and `instance_replace_app_private_key`.

- **Webhook secret.** The server generates the new secret and pushes it to GitHub itself; it is never shown. If GitHub refuses, nothing changes and the old secret stays current. The old one also verifies for the overlap (default and at most one hour), then only the new one does.
- **Private key.** Generate a new key in the App's settings on GitHub and upload the file. The server checks it with `GET /app` for the same App before it swaps; a bad file or another App's key is refused and the old key stays. Afterwards, delete the old key on GitHub.

## Installation tokens

Installation access tokens come from one function. It signs a short-lived App JWT, asks GitHub for a token scoped to the repositories and permissions of the call, and caches it until about five minutes before it expires. Tokens are never logged or returned by an operation.

## Troubleshooting

### `checkout_auth_failed`

A run of a private repository ends `infra_error` with "the checkout was refused by GitHub (HTTP 401): check that the Turntable CI App installation can read this repository". The attempt has the infra kind `checkout_auth_failed` and is not retried, because retrying cannot help. Check that:

- the repository is bound to the App installation (the run's repository shows an installation);
- the installation has access to this repository (on GitHub: Settings, Applications, the App, Repository access);
- the App has the `Contents: Read` permission and the installation accepted it.

The checkout asks for a token scoped to that one repository with `contents: read` only. After you fix the access, re-run the job.

## Other commands

`turntable github-app status` lists the App and its installations (no secrets).
