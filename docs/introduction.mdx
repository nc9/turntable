Turntable reads GitHub Actions workflow YAML and runs it outside GitHub. Each job runs in its own disposable sandbox, on the provider you choose. It ships as a single Bun binary with a built-in web UI.

<Warning>
  Turntable is pre-alpha. Interfaces change without notice, and no release has been published yet. Pages mark work that is not built as not built.
</Warning>

## Why Turntable

- **MCP-first, agent-native.** Everything is drivable through MCP and a REST API with OpenAPI 3.1, both generated from one operations registry. No capability is UI-only or CLI-only. Agents follow a realtime event feed. Signed outbound webhooks are not built yet. See [Agent interface](/agent-interface).
- **Secrets never enter sandboxes.** A secrets proxy injects credentials into outbound requests per allowed host, so job code and third-party actions never hold raw secrets. See [Secrets proxy](/secrets-proxy) and [Security](/security).
- **Pluggable providers.** Docker and Daytona come first. Anyone can write a provider that runs out of process over JSON-RPC. See [Providers](/providers).
- **One binary, SQLite to Postgres.** Start with a single file and a SQLite database. Move to Postgres when you need to scale. See [Architecture](/architecture).
- **Honest compatibility.** Unsupported workflow features fail loudly at parse or plan time. They are never silently ignored. See [Compatibility](/compatibility).

## What exists today

A server that polls or receives GitHub webhooks, plans workflows and runs one job per sandbox through act, on Docker or Daytona, with live logs in a web UI. Around it: org-scoped tenancy and quotas, a secrets vault and proxy, per-org OIDC, trust classes for pull requests, a control-plane cache, artifact provenance, human approvals, a separate release lane with signing and publishing, an audit chain, and incident freeze. Everything is reachable through MCP and REST. [How the pieces fit](/overview) is the shortest tour.
