title: Secrets vault
description: How Turntable stores, scopes and audits secrets, and what it defends against.
---

This page is the design and threat model for the built-in vault. It covers storage, scoping, policy, rotation and audit. Secrets reach jobs only through the [secrets proxy](/secrets-proxy), which attaches them to requests outside the sandbox; nothing hands a value to a sandbox.

## Goals

- A secret is only ever usable by the runs, in the places, that its owner said.
- A fork pull request, or anything that is not positively trusted, never gets one.
- A value never leaves the vault through an API response, a log line, an error, the audit log or an export.
- A stolen database alone reveals nothing. A stolen master key alone reveals nothing.

## Threat model

| Threat | Defence |
| --- | --- |
| Database read (backup, SQL injection, leaked file) | Values are sealed with AES-256-GCM under per-record data keys that are themselves sealed under a key derived from the master key. The master key is never in the database. |
| Record moved or swapped inside the database | The AAD binds domain, org, secret id, version and name. A moved or edited record fails to open. |
| A job, a fork PR or an agent asks for a secret | Policy is evaluated by the core, never by the caller. The class comes from the run's stored post-demotion decision. `untrusted_pr` can never be allowed. |
| A secret used somewhere it should not be | A secret names its allowed destination hosts. An empty list means nowhere. |
| A prompt-injected agent reads or leaks values | No operation returns a value. `set_secret` and `rotate_secret` are not exposed over MCP, so a value never sits in an agent's context. |
| Value ends up in logs or the audit chain | Operations that carry a value declare it; dispatch redacts it from every audit path. Tests plant a sentinel and search the log, the chain, error bodies and console output. |
| Server child processes inherit the master key path or tokens | Children get an allowlisted environment. A source-guard test fails if code spawns a process without it. |
| Key mixing: the audit signing key or the GitHub App key read or replaced through the vault | System secrets live under a separate key domain and are unreachable from the vault operations. |
| Compromised vault operator token | Writes need `release_operator` or `admin`; every write, denial and use is audited in the hash-chained log. |

Out of scope here: a compromised server process (it holds the master key in memory), a malicious operator with the master key, side channels, and secrets in a job's own memory once delivered.

## Key hierarchy

```
master key (file, 32 bytes, outside the database)
  |-- HKDF "system" domain key, per org -> GitHub App key, webhook secrets, audit signing key
  |-- HKDF "oidc" domain key, per org   -> OIDC signing keys
  |-- HKDF "job" domain key, per org    -> vault secrets
        |-- per-version data key (random, one per sealed value)
```

Each domain key is derived with HKDF-SHA256 from the master key and the domain name, so a record sealed for one domain cannot be opened as another even with the same org and name. The AAD also carries the domain, the org, the secret id, the version and the name. Records written before domains existed (`v1`) still open and are re-sealed in the new format the next time they are written. Re-sealing is forward-only: an older Turntable cannot read a `v2` record, which matters for rollback.

### Per-org keys

The key that wraps a value is derived from the master key, the domain and the org id (format `v3`). A value sealed for org A therefore opens with A's key only, whatever AAD is presented: moving a record to another org fails on the key as well as on the AAD, and a mistake in one org's AAD cannot expose another's values. This limits what a bug does; it does not protect against the master key itself, which still derives every org's key. Per-org keys held in a KMS are the way to take the master key out of the picture.

Records written before this (`v2`, per domain only) still open. Convert them in place, once per org, after upgrading:

```sh
turntable keys reseal --org <slug>
```

It re-seals the secret store, the OIDC keys, the vault versions and the audit anchor state for that org; values and versions do not change. Once every org is done, set `TURNTABLE_REQUIRE_ORG_KEYS=1` and a record that is not per-org is refused wherever an org is known, so a stale copy of an old record cannot be put back. `keys reseal` itself refuses to run while it is set, for the same reason: re-sealing reads an old record, and in strict mode that would turn a stale copy into a fresh one. To reseal again, unset it, run the reseal, and set it again. As with the earlier format change, this is forward-only: an older Turntable cannot read a `v3` record. The release lane's own signing keys and attempt credentials have no org and stay per domain.

## Scopes

A secret is bound to:

- an org (always) and optionally a project,
- an optional environment name,
- an optional ref pattern (`main`, `release/*`),
- the trust classes allowed to use it (default `protected` and `release`; `untrusted_pr` is refused at write time and again at use),
- the destination host patterns it may be sent to (default none).

The same name can exist under different scopes (a `DEPLOY_TOKEN` per environment). When several secrets with one name match a use, the most specific wins: project beats org, environment beats none, a ref pattern beats none. Two matches at the same specificity are an error, never a guess.

## Policy

One function decides every use. It is given ids (run, job, attempt) and loads the run's stored class itself. The caller cannot pass a class. A use is allowed only if all of these hold:

1. the secret's scope matches the run (org, project, environment, ref),
2. the run's class is in the secret's allowed classes,
3. the class may be given secrets at all (`credentialsFor(class).secrets`),
4. for a delivery, the destination matches one of the secret's host patterns.

Any other answer is a denial, and denials are audited.

## Versions and rotation

Every write creates a new version. `rotate_secret` makes the new version current and keeps the previous one usable for an overlap window (default 0, at most 7 days), so a run that already started with the old value can finish and a downstream system can be updated. After the window, the old version is refused. Deleting a secret deletes every version.

## Audit

Every write is audited by name and scope, never by value. Every use is audited with the secret, the version, the run, job and attempt, and the destination. Denials are audited with the reason. All of it goes into the per-org hash chain (see [Security](/security)).

## Environment of child processes

The server starts processes (git, act, docker, sandbox helpers). Each one gets only an allowlisted environment (`PATH`, `HOME`, locale and a few named extras per call site). The master key path, bootstrap token hash, API tokens and the rest of the server's environment are never passed on.

## 1Password

A vault secret can be a reference into 1Password (`op://<vault>/<item>/[section/]<field>`) instead of a sealed value. The value is read on the control plane through a service account, at use time, through the same policy path as a sealed secret: trust class, scope, destination and audit all apply, and the secrets proxy injects it. A sandbox never holds the reference, the value or the service-account token.

### Configuration

Service accounts are operator config, never database rows. Set `TURNTABLE_OP_CONFIG` to a file path, or `TURNTABLE_OP_CONFIG_JSON` to the document:

```json
{
  "cacheTtlSeconds": 300,
  "canary": "op://ci/health/check",
  "accounts": [
    {
      "name": "ci",
      "tokenFile": "/run/secrets/op-ci-token",
      "vaults": ["ci"],
      "orgs": ["<org id>"],
      "trustClasses": ["protected"],
      "hourlyReadLimit": 1000
    }
  ]
}
```

- Each token is read from `tokenEnv` (the name of an environment variable) or `tokenFile`, never from the document, and never logged. Every token is registered with the log redactor of every attempt.
- `vaults` lists the 1Password vaults the account serves. A vault is served by exactly one account. A reference whose vault no account serves cannot be bound.
- An account serves the `orgs` and `projects` (ids) it names and the `trustClasses` it names, and nothing else. A use outside that is refused as `account_not_bound` and audited. A job in a class the account is not bound to can never resolve through it, so an account bound only to `release` is never used by a CI job.
- The release lane reads its own configuration from its own environment, so the release account's token is held by that process alone. Do not put it in the main process's configuration.
- The 1Password SDK, and its 14 MB WebAssembly core, is loaded on the first read. An instance with no 1Password configuration never loads it. The compiled binary embeds the core, so it runs from an empty directory.

### Using it

`bind_secret_reference` points a secret name at a reference (admin only, audited); `unbind_secret_reference` removes it. A bound secret has `source` `onepassword`, no sealed versions and `current_version` 0. `set_secret` and `rotate_secret` refuse it, and a sealed secret is never converted in place. `refresh_secrets` drops the in-memory cache. `doctor_secrets` resolves the configured canary reference live and reports whether 1Password is reachable, with each account's reads in the last hour and its remaining hourly quota when `hourlyReadLimit` is set. The daily per-account limit is not tracked: see the 1Password account. It never returns a value.

These four operations (`bind_secret_reference`, `unbind_secret_reference`, `refresh_secrets`, `doctor_secrets`) are deliberately admin-only and not on MCP. Binding and refreshing are human or operator acts, available through REST and the CLI. A bind is refused unless an account configured for this org, or for a project of it (the project itself for a project-scoped bind), serves the vault. "No such vault" and "not yours" give the same error, so a bind never reveals which vaults are configured for other tenants.

### Caching, limits and failure

- Values are cached in memory only, per account and reference, for `cacheTtlSeconds` (default 300; 0 turns the cache off). They are never written to disk. A changed value is picked up after the TTL, or at once after `refresh_secrets`.
- Concurrent misses for one reference make one read. After a rate limit (HTTP 429) the account is blocked locally for 30 seconds, doubling up to 15 minutes while it keeps failing, so a limited account is not hammered. Service-account limits are per token per hour and per 1Password account per day, so a few dozen references on a small plan can use the day's budget: keep the TTL long.
- It fails closed. An outage, a rate limit, an auth failure, an unknown reference, an empty value or a read that takes more than 15 seconds refuses the use as `backend_unavailable`. The job's request gets a 502, and an attempt that then fails reports an infra error so it can be retried. A value past its TTL is never served.
- Every resolution and refusal is audited with the secret name, the 1Password vault, item and field names, the account name, the run and the attempt. Never the value. The log line for a rate limit or a rejected token names the account and the remaining quota, never a token.

### Threat model

The service-account token is the root of trust for every vault it can read. Anyone who holds it reads those vaults directly, with no policy and no audit here. So:

- Use one read-only service account per 1Password vault.
- Split vaults by trust class: one vault and account for CI, a different one for release. Bind each account only to the classes that need it.
- Give every token an expiry and rotate it. An expired or revoked token fails closed.
- Keep signing keys out of these vaults. They belong in the [signer](/signing) (KMS), never in anything a CI job's policy path can read.
- Store the token in a file readable only by the server's user, or a platform secret, not in the configuration document.

This protects against a job, a workflow or a fork reading a secret it was not granted, and against a 1Password outage handing a job a stale or empty value. It does not protect against someone with the service-account token, a compromised control-plane process (it holds the tokens in memory), or an admin who binds a secret to a destination they control.

## Not built yet

Other external stores (Vault, AWS Secrets Manager, GCP Secret Manager), which can reuse the `source` and `external_ref` columns, a KMS-held master key, the write-only UI and proxy token exchange are tracked separately.
