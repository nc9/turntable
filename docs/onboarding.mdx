title: Connecting repositories
description: The onboarding wizard at /onboarding, what each step grants, and how to undo it.
---

The web UI has a guided way to connect an org and its repositories, and it ends with a first CI run. Open `/onboarding`, or press **Connect repositories** on the org list, on the empty state of a new org, or in the org switcher. It works the same on a self-hosted and a hosted instance.

You must be signed in with GitHub (see [web sign-in](/web-sign-in)). An API token cannot create orgs or install the App, so the wizard asks you to sign in when you only hold a token.

## The steps

1. **Org.** The wizard lists the orgs you belong to. Orgs where you are an owner or admin can be chosen; connecting repositories needs one of those roles. **Create org** takes a slug (lowercase letters, digits and dashes) and a display name, and makes you the owner. On an instance that has not turned on self-serve orgs for your account, the refusal text from the server is shown as it is (see [the account principal](/security#the-account-principal-and-self-serve-orgs)). You may create 3 orgs in 24 hours.
2. **Install the App.** A modal explains what the GitHub App is granted, then **Install on GitHub** opens GitHub in a pop-up window. The modal continues on its own when GitHub sends you back. If your browser blocks the pop-up, the modal offers a link that continues in the same tab and a link back to `/onboarding?step=repos`. If the App is already installed, **Already installed? Pick the installation** lists the installations GitHub shows you. One that is connected to a different Turntable org is greyed out and labelled "connected to a different Turntable org"; Turntable never moves an installation.
3. **Repositories.** A table lists every repository the installation grants. Each is marked **new** or **already in this org**, with a tick box and a checks mode (below). A new repository starts unticked at Off. For a repository already in the org, leaving its mode alone keeps the mode it has. **Grant more repos on GitHub** reopens the installation's configure page on GitHub; when you return, the table refreshes.
4. **Workflow preview.** For each enabled repository, Turntable reads the workflow files at the default branch and shows what it would do with each job: `run`, `skip` (its `if:` is false) or `fail` (Turntable cannot run it, with the reason and how to fix it). Nothing runs. Workflow and job names come from the repository and are shown as plain text. A file over the preview budget is listed as too large, and a note says when more files exist than the preview reads (50).
5. **First run.** **Run CI now** starts a run of the default branch head and links to the live run page. The finish screen shows the run's conclusion, failed jobs with their reasons, and the jobs Turntable refused with the fix. Next steps: **Go live**, the exact `turntable / <job>` check names to require in a GitHub ruleset (each copyable), and how to invite teammates. A repository with no workflow Turntable can run shows a short sample to add, and you press **Run CI now** after you push it.
6. **Enrol your passkey (optional).** The finish screen links to the org's Approvers page, where an owner enrols a passkey as the org's first approver (needed to approve releases and sensitive changes). It needs a GitHub sign-in from the last 10 minutes; see [Hosted](/hosted#the-first-approver-on-a-host-with-no-shell).

## What each step grants

| Step | What it does |
| --- | --- |
| Create org | Makes an org with the instance's default quotas, with you as owner. |
| Install the App | GitHub shows its own consent page. The App gets **checks: write**, and **contents**, **metadata** and **pull requests: read**. It cannot push code or change settings. Turntable checks that you own the installation before it connects it, and records who did. |
| Repositories | Creates a project for each ticked repository and turns CI on for it. The projects a pop-up install creates start paused until you tick them here. |
| Checks mode | Chooses what Turntable posts to GitHub, per repository. |
| Run CI now | Starts one run of the default branch as a push run. The default branch is a protected ref, so its trust class is `protected`. |

The checks modes use the same words everywhere:

- **Off**: runs on Turntable, posts nothing to GitHub (default).
- **Shadow**: posts neutral `shadow / <job>` checks that never block.
- **Live**: posts `turntable / <job>` checks your rules can require.

Changing a mode needs an owner or admin. A value locked by the environment or `turntable.toml` is refused with the server's own text.

## Go live and required checks

Start in Off or Shadow, look at a run or two, then press **Go live** on the finish screen (or set `checks_mode` to `live` in the project's settings). Then, in your GitHub ruleset, add the names the finish screen lists under **Require status checks**. Copy them exactly: a job in a matrix has its leg in the name. A required check that never reports blocks merges, so only require names after a live run has posted them.

## How to undo it

- **Stop CI for a repository:** untick it on the repositories step and continue. That pauses its project; nothing is deleted, and ticking it again lifts the pause.
- **Stop posting to GitHub:** set the repository's mode back to Off.
- **Remove the App:** on GitHub, open Settings, Applications, Installed GitHub Apps, choose the App and uninstall it or remove single repositories. Turntable can no longer read those repositories or post checks to them.
- **Remove a ruleset requirement:** edit the ruleset on GitHub.

## Notes for operators

- The page needs sign-in to be configured: a master key, a GitHub App and an https public URL. See [web sign-in](/web-sign-in).
- The install pop-up reports back to the page that opened it with a `postMessage` to the instance's own origin, and the page ignores any message from another origin or for another claim. The message is only a prompt: the page then reads the claim from the server, and it also polls the claim every 5 seconds for up to 2 minutes, because a web session cannot open the realtime socket.
- `/onboarding` is served with a `Cross-Origin-Opener-Policy` header that lets the pop-up keep its link to the page.
- The wizard calls these REST operations: `list_my_orgs`, `onboarding_create_org`, `list_user_installations` (these three take a signed-in web session and nothing else), `start_installation_claim`, `get_installation_claim`, `bind_installation`, `list_installation_repos`, `onboard_repos`, `preview_workflows` and `run_default_branch`. None is an MCP tool. See [the agent interface](/agent-interface).
