The hosted instance deploys itself. This page describes the scripts in `scripts/cd/`; the workflow that runs them is `.github/workflows/deploy.yml`, reviewed by a maintainer. The scripts take injected `fetch`, GraphQL, git and clock functions, so their tests run against fakes and make no live call.

## What triggers a deploy

A successful CI run on `main` (a `push` run, not a pull request) starts the deploy workflow for that exact commit. Runs are serialised and never cancelled, and the newest green commit wins: a deploy of an older commit is held (see below), so a batch of merges deploys once. The workflow runs in the `production` environment.

## The preflight and its holds

`scripts/cd/preflight.ts` returns `{ deploy, held, migrations }`. It deploys only when nothing holds it. A hold stops the deploy and names its reasons.

| Hold | Why |
| --- | --- |
| CI for the target is not `success` | Never deploy red. |
| The target is not the newest green `main` commit | A newer commit will deploy instead. |
| A new migration is not additive | The old release may break on the new schema, and a rollback would too. |
| The target changes `.github/workflows/deploy.yml`, `scripts/cd/**`, `Dockerfile` or `railway.*` since the deployed commit | The pipeline that deploys itself needs a human review of its own change. |
| No previous successful `production` deployment | Nothing to compare against. |
| The agent-facing API surface changed in a way other than a new optional response property | Customers' tooling reads these operations. See [API-surface hold](#api-surface-hold). |
| The check-run name builder changed | A branch-protection rule matches check-run names. |

The deployed commit is the one in the last successful `production` deployment record.

### Migration classes

`scripts/cd/migrations.ts` reads the new entries in both drizzle journals (`packages/core/drizzle` and `packages/core/drizzle-pg`) between the deployed and target commits. It splits each file into statements (drizzle's `--> statement-breakpoint` markers, then `;`) and classifies each statement.

Additive: `CREATE TABLE`, `CREATE [UNIQUE] INDEX`, `ALTER TABLE ... ADD [COLUMN]` for a nullable column or one with a `DEFAULT`, and a foreign key added to a table created in the same migration.

Not additive: everything else. That includes `DROP`, `RENAME`, `ALTER COLUMN`, a `NOT NULL` column without a default, a constraint on an existing table, `UPDATE`, `INSERT`, `DELETE`, `PRAGMA`, and the SQLite table rebuild (`CREATE TABLE __new_x`, `INSERT INTO __new_x`, `DROP TABLE x`, `ALTER TABLE __new_x RENAME`), which starts like an additive change and is not. A file is additive only when every statement is. The classifier test asserts a class and a reason for every migration file in the repository, so a new migration cannot land without its class being written down.

### API-surface hold

Between the deployed and the target commit, preflight diffs `docs/openapi.json` for these operations: `checks_for_sha` (`/api/v1/checks/{sha}`), `failure_digest`, `job_log`, `list_runs`, `get_run`, `events`, and every release and approval operation (any operation whose name contains `release` or `approv`, such as `request_release`, `get_release_request`, `approve_run`, `approve_release` and `submit_approval`).

The only change that passes is a new optional property in a response schema. Everything else holds: a path, method, parameter or security change, any request-body change, a removed or renamed property, a type change, a property that becomes required, a removed or added enum value, and an operation added to or removed from the watched set. Description, title, summary and example text is ignored.

MCP tool names and inputs come from the same operation registry, so preflight also diffs the tool list for the same operations. The list is `docs/mcp-tools.json` (name and input schema only), generated by `bun run scripts/mcp-tools.ts --write` and kept current by a test, so `git show <sha>:docs/mcp-tools.json` gives the list at any commit. A commit that lacks either document cannot be compared and holds.

**Check-run names.** The names come from `checkName` and `checkScopeOf` (with their text cleaner) in `packages/core/src/checks/mapping.ts`; the reporter and `checks_for_sha` both call them. Preflight holds when that file differs between the two commits. It is coarse: any edit to the file holds, and a maintainer reads the diff and deploys by hand if the names are unchanged.

### Poll-config changes

CD never sets environment variables. A change to the poll configuration that touches a customer's project (for example the repos or workflows a project ingests) is held and announced to that customer with a note first, even when a maintainer stages it by hand. It is never a side effect of a deploy.

## The deploy gate

A deploy restarts the instance, and a restart must not cut a release. `GET /api/v1/deploy-gate` is a public endpoint (no credential) that returns only:

```json
{ "safe": false, "reason": "release_in_flight" }
```

`reason` is `ok` (with `safe: true`), `release_in_flight` or `draining`. It is `release_in_flight` while any of these exist anywhere on the instance:

- a run of the release trust class that is queued, running or awaiting approval;
- an attempt running as the release class;
- a job awaiting approval in its project's signing environment;
- a release request that is `pending` or `claimed` (the release lane claims a request before it verifies, signs and publishes, and finishes it after the publish step);
- an unspent, unexpired approval for the signing environment (a co-sign gathered or complete, not yet spent by the signature).

It is `draining` while a drain is on and no release is in flight.

The answer is the same for every caller and carries no org, project, run or job id, name or count. It reveals one bit on purpose: the endpoint is unauthenticated, so anything more would publish one customer's activity to everyone. The answer is cached for at most 15 seconds, the response is `Cache-Control: no-store`, and each client address gets at most 60 requests a minute (the same client-address rule as the webhook limiter, honouring `TURNTABLE_TRUSTED_PROXIES`); beyond that it answers 429. If the database cannot be read it answers 503 with `safe: false`: an unknown state never opens the gate.

`scripts/cd/gate.ts` polls the gate until `safe` is `true`. Anything else (a `false`, an error, a 429, a malformed body) keeps it waiting. After 6 hours the run fails and pages: "deploy waited 6 h for a release to finish".

### Drain cuts

When a drain times out, the server marks each still-running attempt as cut by the drain, and the next boot re-attaches to its exec or requeues the job once under a new attempt (never as a job failure). This does not depend on the trust class: protected and release attempts are requeued the same way. The deploy note reports only how many attempts were cut and requeued. The named list goes in the private rollout log.

## Backup and prune

Before the deploy, `scripts/cd/backup.ts` creates a platform volume backup (`volumeInstanceBackupCreate`) and polls `volumeInstanceBackupList` until a backup newer than the start time appears. If none appears before the timeout, the deploy aborts. It then keeps the newest 3 backups: while more than 3 exist, it deletes the oldest, one at a time, waiting until each is gone and retrying when the platform answers "Backup deletion already in progress". It never deletes the new backup and never deletes while 3 or fewer exist.

## Verify and rollback

`scripts/cd/verify.ts` polls `/healthz` until it reports `"ok": true` and a `build_sha` (or `version`) equal to the target commit, or the timeout passes. During the drain the old instance still answers with its own sha, so a mismatch is retried and only fails at the timeout.

The image build writes the deployed commit from a `BUILD_SHA` file at the repository root into the binary. Without that file (a local build) `build_sha` is `unknown`. `/healthz` is the unauthenticated version route; it also reports `built_at`, and `version` is the full build version (see [Build version](#build-version)).

If verification fails and no migration ran, the workflow redeploys the previous commit and publishes the rollback note `rolled back <target> to <previous>: <reason>`. `verifyDeploy` returns the plan (`redeploy` with the note, or `stop` with the reason), so the workflow decides from its result. If a migration ran, it stops and notifies: the database is never restored automatically, because that would discard data written since the backup. Restoring a backup is a maintainer's decision.

## Build version

Every build has a version of the form `<base>-dev<N>+<sha8>`, for example `0.1.0-dev7+594b21af`. The base is the root `package.json` version. `N` is not committed and no git tags are created; the operator bumps it per deploy. The same string is the `Turntable-Version` response header, `/healthz` `version`, MCP `serverInfo.version`, the served OpenAPI `info.version`, `turntable version` and the label in the web UI. The web UI shows a "new version available" banner when the server answers with a different version than its bundle. Compare versions with equality only: `dev10` sorts before `dev9` under semver rules, so nothing orders them.

A cross-origin browser caller cannot read `Turntable-Version` unless the proxy in front sends `Access-Control-Expose-Headers: Turntable-Version`; Turntable sets no CORS headers itself.

The build resolves the version in this order: the `TURNTABLE_VERSION` environment variable, then a one-line `BUILD_VERSION` file at the repository root (next to `BUILD_SHA`), then `<base>-dev0+<sha8>` (`+unknown` without a `BUILD_SHA`). A supplied value is used verbatim and a malformed one fails the build. A tagged release passes `TURNTABLE_VERSION=<tag without v>`.

The deploy contract, for the operator's script:

1. Read the running version from `GET <instance>/healthz` (`.version`, or the `Turntable-Version` header of any response). Match it with `^(\d+\.\d+\.\d+)-dev(\d+)(\+.*)?$`.
2. If the running base equals the base in the repository being deployed, the next version is `N+1`. If the base changed, or the running version is not a `-dev` one, `N` is `0`. The result is `<base>-dev<N>+<sha8>`, with `sha8` the first 8 hex characters of the deployed commit.
3. Pass it as `BUILD_VERSION` in the archive root or as `TURNTABLE_VERSION`.
4. Verification keeps matching `build_sha`; it may also assert `version` equals what was passed.

A deploy that never went live leaves `N` unused, because the next deploy re-reads the running one. No state lives outside the running instance.

## Deploy notes

`scripts/cd/notes.ts` builds a markdown note for the GitHub Deployment record and the deploy log issue: the pull requests merged between the two commits, each migration with its class, the backup id, the timings and, when a drain cut running attempts, the count of attempts cut and requeued (never their names). Pull request titles are escaped so they render as text.

## Deploying a held commit by hand

A held commit does not deploy until a maintainer reads the hold reasons and the diff, for a migration that means checking that the old release still runs on the new schema (or accepting the downtime). Then run the deploy workflow by hand (Actions, `deploy`, "Run workflow") for that commit with the acknowledgement input set. A manual run lifts the migration and pipeline holds only. A red CI or a commit that is not the newest green one still stops it. The backup, verify and notes steps run as usual.
