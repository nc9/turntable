title: Signing in to the web UI
description: Sign in with GitHub, sessions, who may join an org, and the first-user bootstrap.

People sign in to the web UI with GitHub, through the instance's own GitHub App (user-to-server OAuth on the App, not a separate OAuth App). The same code serves a self-hosted and a hosted instance. What a person may do comes only from Turntable's own membership rows, never from GitHub.

## Turning it on

Sign-in is on when the instance has a master key (`TURNTABLE_MASTER_KEY_FILE`), a GitHub App and an https public URL (`TURNTABLE_PUBLIC_URL`; `localhost` is allowed for a trial). The session cookie is `Secure` and uses the `__Host-` prefix, so a public URL that is not https leaves sign-in off, with a warning at boot. Without it, no session cookie is a credential anywhere and every `/auth/*` path is unclaimed.

In the App's settings on GitHub, check two things:

- **Request user authorization (OAuth) during installation** is on (the claim flow needs it too).
- The callback URLs include `<public url>/auth/github/callback`. An App created by the hosted manifest flow in claim mode already lists it next to `<public url>/api/v1/github/setup`. Add it by hand to any other App.

The App needs no new permission: user authorization only reads the signed-in user's id and login.

## The flow

1. `GET /auth/github/login` builds a `state` (an HMAC over a random nonce and an expiry, 10 minutes). The nonce is stored once in `login_states` and set in a short-lived `HttpOnly`, `Secure`, `SameSite=Lax` cookie, `__Host-tt_login_<tag>`, where `<tag>` is a short hash of the nonce: each sign-in has its own cookie, so two tabs signing in at once both finish, and a browser keeps at most four (the earliest are expired). The state key is created once with insert-if-absent and always read back from the secret store, so every server process over one database signs with the same key. The browser goes to GitHub's authorize URL for the App, with an explicit `redirect_uri`. There is no `return_to` parameter: a finished sign-in always lands on `/`.
2. GitHub sends the browser to `GET /auth/github/callback`. The state's signature and expiry must hold and the cookie named for the state's nonce must hold it, exactly. Only then is the nonce spent, atomically, so a replayed state fails. Only after that is the code exchanged and the user read (`GET /user`). The user's token is dropped at once.
3. The identity is the **numeric GitHub user id**, kept in `github_identities`. The login is stored for display and for matching invites; a rename changes nothing.
4. If the person has no membership and no live invite, nothing is written and the page says so. Signing in never grants an org: there is no auto-join by repo access or GitHub org membership.

## Sessions

A session is a row in `web_sessions`. The browser holds a random 256-bit id in `__Host-tt_session` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`); the database holds only its SHA-256, so a database read yields no usable cookie.

| Setting | Default | Meaning |
| --- | --- | --- |
| `session_idle_hours` | 12 | Signed out after this long unused. |
| `session_absolute_days` | 7 | Signed out after this long, however active. |

Both are instance settings (environment, `turntable.toml` or `instance_set_setting`). Sign-out (`POST /auth/logout`) revokes the row.

A session is a credential for the REST API only (`/api/v1`). MCP, the realtime socket and the event stream stay bearer-token only. A request that carries an `Authorization` header is judged as a bearer request, and its cookie is ignored.

A session resolves to a `member` principal for **one org**, with the role in that org's `org_members` row. A person in several orgs names the org in the call (`org`); a person who is not a member gets the same `not_found` as for an org that does not exist.

### CSRF

Every state-changing request from a session must carry an `Origin` header equal to the configured public origin. A missing `Origin`, `null`, or a look-alike is refused (403). The origin is the configured one, never the request's `Host`. The sign-out form also carries a token derived from the session id. Requests with a bearer token are unaffected.

### What a session may do

A session may call every read operation its role allows, and two writes with no step-up: `invite_member` for a viewer or member, and `session_step_up_challenge`. A few sensitive writes are open to it only with a fresh passkey step-up (see below). Every other write is refused, and the refusal is audited. The rules are default-deny lists in the dispatcher (`SESSION_WRITE_OPS`, `SESSION_STEP_UP_OPS`), so a new write operation is closed to sessions until someone opens it.

## In the web UI

Any logged-out visit to the app ends on `/sign-in`. Its main button, **Sign in with GitHub**, goes to `/auth/github/login`. A small **Use an API token** link opens `/sign-in/token`, the token form for agents, scripts and break-glass use; it is never the landing page. A `next` parameter on the sign-in URL is kept only when it is a same-origin relative path.

When the page loads, it asks `GET /auth/session`. If you are signed in, the UI runs on the cookie session and stores no token in the browser. Your orgs come from the session, an org switcher in the header lists them, and the last org used in this browser is remembered (and checked against your orgs, so a stale one is ignored). After the GitHub callback you land in that org, in your only org, or on an org picker. **Sign out** in the switcher menu posts to `/auth/logout` and returns to `/sign-in`.

Two things differ from token mode:

- **Updates are polled.** The realtime socket and the event stream accept only a bearer token, so a session refreshes lists and logs every few seconds instead of streaming them.
- **Some writes are refused.** A session can only invite members. The UI says "This needs passkey confirmation." where a passkey step-up exists, and "Use an API token for this" for every other write.

## Who may join: invites and the bootstrap

Membership is created in one of two ways, never automatically.

- **`invite_member`** (`POST /api/v1/members/invites`, not an MCP tool): `{github_login, role}`. Callable by a person's own token with `release_operator` or above, or by a signed-in admin or owner. A token may invite a viewer or member only; a signed-in **session** may also invite only a viewer or member unless it carries a passkey step-up for that exact invite (so a stolen session cannot mint a persistent owner); a member may not invite above their own role; an agent token is refused. The invite lasts 7 days, and a newer invite for the same account replaces the older one. The org feed gets `org.member_invited`.
- **`instance_bind_github_login`** (`POST /api/v1/instance/member-bindings`, a `tti_` token only, REST only): `{target_org, github_login, role, reason}`. The instance administrator uses it to give a new org its first admin or owner. It is audited in the system org's chain and in the org's own, and the org's feed gets `org.member_invited`. This is the only root of an admin or owner on an org with no admin who can invite.

Both resolve the login to its **numeric GitHub user id when the invite is created** (`GET /users/{login}` with the App's credentials, through the guarded outbound client) and store the id on the invite. If GitHub cannot be asked, or has no such user, the invite is refused. At the invitee's first sign-in, Turntable matches on that id (the login is only for display), so an account renamed since the invite still gets in and a different account that now holds the old login does not. It binds the identity, consumes the invite and adds the membership in one transaction, emits `org.member_joined` and audits it as `member_joined`. An existing member keeps the role they have.

## Passkey step-up

A session cookie alone can read and make low-risk invites. For the actions below, the signed-in person must also prove a **fresh passkey assertion** from their own enrolled passkey.

| Action | Needs step-up |
| --- | --- |
| `create_api_token` | Always (the signed-in person must be an admin or owner). |
| `invite_member` | Only for the `admin` and `owner` roles. |

Not yet covered, and still refused for a session (use a token or the instance operator): approver and enrolment changes, and loosening a setting. Approvals themselves already need a signed statement, so a session cookie never approves anything.

**Flow.**

1. `session_step_up_challenge` (`POST /api/v1/session/step-up`) takes `{action, input}`: the action and the exact input it will be called with. It returns a single-use WebAuthn `challenge`, the person's eligible passkeys and an expiry.
2. The browser signs the challenge with that passkey.
3. The sensitive call carries `step_up: {id, approver, signature}` next to its normal input.

**What it is bound to.**

- The action name and a hash of the exact validated input and project scope. A step-up for `create_api_token {role: reader}` cannot authorize `{role: release_operator}`, or a different lifetime or kind.
- The session that asked: another session of the same person cannot use it.
- One use. It is spent when the call is accepted, whether or not the action then succeeds.
- At most **5 minutes**. An expired, reused or wrong-action step-up is refused with `forbidden` and a `details.reason` of `step_up_expired`, `step_up_reused`, `step_up_wrong_action`, `step_up_bad_key`, `step_up_reenrol`, `step_up_bad_assertion`, `step_up_unknown` or `step_up_required`.

**Which passkey.** A WebAuthn approver key enrolled in the org for **the signed-in person's numeric GitHub id**, not revoked and satisfying the org's key policy. The id is recorded at enrolment: `bootstrap_approver` and a token's `request_enrolment` resolve the forge login to its id through the App (and are refused if GitHub cannot be asked), and an enrolment made by a signed-in person for their own login records their session's id. The forge login on an approver is display text for step-up: a renamed account keeps working and a different account that now holds the old login does not. A key with no recorded id (enrolled before this, or by `turntable approvals bootstrap` on the host's CLI) can never satisfy a step-up and is refused with `step_up_reenrol`: re-enrol the passkey. The relying party is the public URL's host, as for approvals. Approval statements are unchanged and keep their own key binding.

**Minting a token from the web.** A step-up'd admin or owner mints a token whose lifetime counts from now. No token's expiry caps it, so this resolves #455: an org whose token lineage ends at a dead root's expiry mints a fresh org token here before then. The existing rules still hold: at most 365 days, the token's role at most the minting person's, and an agent token at most `operator`. Bearer tokens keep their own rules and cannot carry a step-up.
