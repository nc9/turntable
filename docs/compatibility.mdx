---
title: Compatibility
description: Which GitHub Actions features Turntable supports, and how it reports the rest.
---

Turntable promises that unsupported features fail loudly at parse or plan time. It never silently ignores them. Every feature is in one of three states.

| State | Meaning |
| --- | --- |
| Supported | Behaves as on GitHub. |
| Supported with differences | Works, with documented differences. |
| Unsupported | Rejected with an error that names the feature. |

<Note>
  Turntable runs workflows through [act](https://github.com/nektos/act), one job per sandbox. The table below says what v1 supports; rows still being proven against real workflows say so.
</Note>

## Pull request events

Steps see the event as they do on GitHub where it matters: act is given a `github.event` payload built only from forge facts fetched at poll time (for a pull request: `number`, `pull_request.number`, `base.{ref, sha, repo.full_name}`, `head.{ref, sha, repo.full_name}`, `draft`, and `repository.full_name`; for a push: `ref`, `before`, `after`, `repository.full_name`). It is stored with the run, so a re-attach or a rerun sees the same bytes. Titles, bodies, tokens and anything else are never included. The delivered checkout has an `origin` remote (`https://github.com/<owner>/<repo>`, never with credentials), as `actions/checkout` leaves it, so `git fetch origin <sha>` works when the job has network egress.

**Known difference:** GitHub runs `pull_request` workflows on the merge commit (`refs/pull/N/merge`). Turntable runs the pull request head sha. This is deliberate for now, and `github.sha` is the head sha.

## Support

| Feature | Status |
| --- | --- |
| Triggers: `push` (branch and tag filters, `paths`), `pull_request`, `merge_group` | Supported, see [Quickstart](/quickstart) |
| Triggers: `schedule`, `workflow_dispatch` | Not ingested yet |
| `needs`, job outputs, `matrix` (with `fail-fast` and `max-parallel`), `if:`, `continue-on-error` | Supported |
| `concurrency` | Supported with differences: groups are scoped to the repo, and a pull request run's group is rewritten so it cannot cancel the default branch, see [Security](/security#trust-classes-and-fork-pr-gating) |
| Composite and JavaScript actions | Supported, resolved to a commit sha before the run, see [Security](/security#action-pins-and-moved-tags) |
| `GITHUB_OUTPUT`, `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_STEP_SUMMARY` | Handled by act |
| Reusable workflows | Not yet verified |
| Services and job containers | A job that needs docker is skipped with the reason as its log |

## Splitting a job across sandboxes

A heavy job can run as several shards, each in its own sandbox, **without editing the workflow**. The operator configures it per repo (`splits` in the poll config, or `turntable policy set --ingest on ... --splits-json '<json>'` for a bound repo); it is never read from the repository, so a pull request cannot change it.

```json
"splits": [{
  "job": "tests",
  "shards": [
    { "steps": ["Audit engine tests"] },
    { "steps": ["Rules tests"] },
    { "steps": ["Remaining package and script tests"] }
  ]
}]
```

`job` is the job id. Each shard lists the steps (by `name:`, or `#<n>` for the nth step counted from 1) that run only there; 2 to 8 shards, and a step may be in one shard only. Every other step (checkout, setup, anything the rule does not name) runs in every shard, so each shard sets itself up. The only change made to a shard's workflow is `if: false` on the steps another shard owns: no step is added or edited. A step the rule names that no longer exists (a pull request renamed it) is owned by no shard, so it runs in all of them: coverage is never lost, only time.

- **One job to everything else.** The shards are ordinary jobs (`tests[0]`, `tests[1]`, ...) with the job's own name. `needs` waits for all of them; `needs.<job>.result` is the fold (failure if any shard failed, else infrastructure error, cancelled, skipped only if all were, else success); outputs merge with a later non-empty value winning. The forge sees **one check, under the job's name**, running until the last shard finishes, with the fold as its conclusion and each shard's result in its summary. In the UI the run page shows the shards as one job row (its name, the folded state and the wall time) that opens to one row per shard, with the step it owns, its attempts, its duration and its own rerun. `turntable parity` treats the shards as one job and reports the wall time from the first shard's start to the last one's finish, not the sum.
- **Failure.** Shards never cancel each other (a job's steps already run every suite even when one is red). An infrastructure error in one shard is an infrastructure failure of the job. Cancelling the run cancels every shard. A shard can be rerun alone (the others keep their results); the rerun reports its own check with the fold of the latest result of each shard.
- **Limits.** Each shard counts against the project's and the org's concurrency caps like any job, and pays its own setup. A job with `strategy.matrix`, or whose declared outputs read the output of a step a shard owns, is not split and runs whole; the run's plan says why (`splitNotices`).

- **Running only the shards whose paths changed.** A shard may carry `paths`, a list of globs in the workflow path-filter syntax (`!` negation included, the last matching pattern decides): `{ "steps": ["UI tests"], "paths": ["packages/ui/**", "!packages/ui/docs/**"] }`. The shard runs only when a changed file matches; a shard with no `paths` always runs. An empty list or a bad glob is a config error when the config loads.
  - **Which files.** The same set the workflow's own path filters use: a pull request's diff against its base, a push's before..after, and for a merge group the queue commit against the group's base. A rename counts under its old and its new path, and a deleted file under its path. The files come from the forge's compare of the commit range at ingest, never from the repository, so a pull request can only change which shards run through its own diff, never the config.
  - **Unsure means run.** With no before commit (a new branch, the first push seen), a force push that removed the base, a compare that failed, a diff larger than one poll will page through, or an empty list, every shard runs. A partial list is never used.
  - **Recorded once.** The decision is stored in the run's plan at ingest, and the run's plan notice names its source (for example `shards selected by changed paths (push a1b2c3d4e5f6..d4e5f6a1b2c3, 12 files)`). A rerun of the run, of the job or of one shard uses the stored decision and never asks the forge again. A skipped shard's log says which paths it listed and none changed.
  - **Results.** A skipped shard is ignored by the fold. If every shard is skipped, the job is `skipped`: it reports to the forge exactly as a job skipped by `if:` does (no check is posted), and `needs:` consumers see a skipped job, so a job that needs it with the default `if:` is skipped too. `turntable parity` takes the wall time from the shards that ran.
  - **Not a gate.** A shard limited by `paths` is not a gate for files outside its globs. Do not put a security check behind a path rule unless its globs cover everything it checks.

## Artifacts

`actions/upload-artifact` and `actions/download-artifact` (v4 and up, including the v7 and v8 that Turntable's own release workflow pins) work inside a run when the control plane has an artifact store. Set `TURNTABLE_ARTIFACTS_URL` to the base URL sandboxes reach the control plane at (the same kind of address as `TURNTABLE_CACHE_URL`). act's own artifact server speaks only the old v3 protocol, so Turntable serves the one these actions use: the twirp `ArtifactService` at `ACTIONS_RESULTS_URL`, with Azure block-blob requests for the bytes. upload-artifact v7 and download-artifact v8 both ship `@actions/artifact` 6.3.1. Against v4's client (2.x) it adds `version: 7` and a `mimeType` in `CreateArtifact`, a `digest` in `ListArtifacts` that download-artifact checks against the bytes it received (the step fails on a mismatch), and `archive: false`, which uploads one raw file under its own name instead of a zip. All are handled. Each job gets `ACTIONS_RESULTS_URL` and a per-job `ACTIONS_RUNTIME_TOKEN` for its attempt, which stops working when the attempt ends. The token is redacted from the log. It also travels in the blob URL paths (`/_artifacts/`), so access logs should not record those paths.

- **Scope.** The run, project and org come from the job's token, never from the request. A job reaches only the artifacts of its own run. Downloading from another run (`run-id`, `github-token`) goes to GitHub's API, not here, and is not supported.
- **What is stored.** The client's upload (a zip, or with `archive: false` one raw file), as one blob under `<data dir>/artifacts/<run id>/<name>`. The control plane streams it to disk, hashes it itself (sha256), compares the client's reported hash and size, then records it against the run, job attempt, name, size and digest. A mismatch is refused and nothing is recorded. A name is recorded once per run: a second upload of the same name, `overwrite`, and `delete-artifact` are refused. Names are one plain component of letters, digits and `. _ + -`, up to 200 characters, so an `archive: false` file with a space or other character in its name is refused. A download is served as `application/zip` when the stored bytes start like a zip and as `application/octet-stream` with a `Content-Disposition` file name otherwise; what the client said its `mimeType` was is not used.
- **Limits.** The org's stored-bytes quota (shared with the cache) and `TURNTABLE_ARTIFACT_MAX_GIB` (default 2). An upload that would pass either is refused with a message in the job log.
- **Trust class.** An artifact carries the trust class of the attempt that wrote it. A download is decided against the class of the job reading: the same class or a higher one reads it, a lower class's artifact is refused (the actions have no way to ask for a lower class's artifact explicitly), and a `release` job reads only `release` class artifacts. The refusal is a line in the job log and the artifact looks absent. The digest is recomputed from the stored file before every download, and a mismatch is refused.
- **Retention.** `TURNTABLE_ARTIFACT_RETENTION_DAYS` (default 90) for the whole instance. After it the bytes are removed and downloads fail. The recorded digest stays.
- **Reach.** A job with open egress reaches the store directly, as for the cache, with a credential that can upload and download. A job with egress `none` has no network, but the artifact service is Turntable itself, so a job whose plan has an `actions/upload-artifact` step (read from the plan, so a composite action or a reusable workflow that wraps it is not seen) gets a narrow route through the [secrets proxy](/secrets-proxy): only `POST` of `CreateArtifact` and `FinalizeArtifact` and `PUT` of a blob upload, on the control plane's host and port, and nothing else (every other host, port, method and path is refused by the proxy). Its credential is **upload-only**: it lives at most two hours and for the attempt, and the service refuses it listing, download URLs, deletes and downloads. A job like that cannot download artifacts. This needs `TURNTABLE_SECRETS_PROXY=1`, an `https` `TURNTABLE_ARTIFACTS_URL` whose address is public (the proxy only dials public addresses), and a provider that can confine the sandbox to the proxy (see the table in [Secrets proxy](/secrets-proxy#how-a-job-reaches-the-proxy)); on a provider that cannot, a job with an upload step ends as `infra_error` rather than running with a different network. Without the proxy, a job with egress `none` gets no artifact credential and the actions fail with a missing `ACTIONS_RESULTS_URL`.
- **Release lane.** Set `TURNTABLE_RELEASE_ARTIFACT_DIR` to `<data dir>/artifacts` and the lane signs from what the jobs uploaded. See [Release lane](/release-lane#artifacts-from-jobs).
- **Not supported yet.** Encryption at rest (unlike the cache, the directory is plaintext, so use an encrypted volume), a per-project retention, and downloads from a job with egress `none`.

## Runner labels

What a `runs-on` label does on Turntable:

| Label | Result |
| --- | --- |
| `ubuntu-latest`, `ubuntu-24.04`, `ubuntu-22.04` | The default sandbox class (unless the operator maps the label). |
| `ubuntu-latest-{2,4,8,16}-cores` | A class with that many cpus, only among the operator's `coresClasses`; else the default class. |
| Custom labels (`boat`, `large`) | The operator's label map, else the default class. Always Linux. |
| `macos-*`, `windows-*`, `[self-hosted, macOS]`, `[self-hosted, Windows]` | Refused. The job never reaches a sandbox and its check **fails**. |
| `arm64`, `*-arm` | Refused unless the provider advertises arm64. Daytona offers amd64 only. |

A refused job fails instead of being skipped on purpose: GitHub branch protection counts a skipped or neutral required check as passing, so a skip would let a pull request merge without the job ever running. The check summary names the label and says `If this job should stay on another CI, gate it with if: vars.TURNTABLE_CI != 'true'`. A job whose own `if:` is false (the gate above, set on the project) is a normal skip: that is the explicit opt-out. The same rule covers every job Turntable cannot run (docker, `services:`, `container:`).

## Unsupported in v1

| Feature | Notes |
| --- | --- |
| Windows runners | Not in v1. The job fails with a clear check (see [Runner labels](#runner-labels)). |
| macOS runners | Not in v1. The job fails with a clear check. A future provider plugin could offer them. |
| GitHub artifact attestations | [Turntable signed provenance](/signing) is the substitute. |
| GitHub OIDC claims | Turntable's own OIDC issuer replaces them. |

## Known gaps

Everything found while running real workflows. Each one is a gap with a stated behaviour, not a silent one.

- **`pwsh` exists only where the image has it.** The Turntable runner image includes PowerShell 7. A provider that starts from its own snapshot (Daytona, for example) has `pwsh` only if that snapshot does. A tool that is missing is absent as on a runner without it, so a workflow's own probe works: `if ! command -v pwsh; then echo "::notice::skipped"; exit 0; fi` skips and succeeds. A step that needs it without a probe fails with exit 127 and a log line naming the tool.
- **`services:` jobs fail, with the reason.** A job that declares `services:` is not run: its check fails with `uses services:` and the gating hint below, never `skipped`. There is no service container support in a sandbox.
- **Docker in a sandbox.** A sandbox has no Docker daemon. The planner refuses a job it can see needs one, and its check fails with the reason (`docker` as a command, a `docker://` image, a `docker/` action, a local action that is a docker action or runs docker), with the reason. It cannot see a docker call hidden inside a script such as `bun run test:integration`, so that job starts and fails when the command runs. To keep such jobs off Turntable, gate them with a project variable: set `TURNTABLE_CI=true` on the project (`turntable policy set --ingest on ... --var TURNTABLE_CI=true`) and write `if: vars.TURNTABLE_CI != 'true'` on the jobs that need docker or services. GitHub has no such variable, so the job runs there as before. The opposite gate (`if: vars.TURNTABLE_CI == 'true'`) adds a job that runs only on Turntable, for example a variant of a database test that runs in-process.
- **Interpreters that a setup action puts first get no shim.** Turntable puts a shim on `PATH` for `node`, `python` and `pwsh`, which keeps steps off a terminal and makes `command -v` behave as on GitHub. The shim is linked only for an interpreter that exists, so `command -v` fails for one that is absent. Each shimmed step re-checks at start and at exit and links a shim for a tool installed behind the shim directory during the job (for example `pwsh` installed with apt), so it is wrapped from the next shimmed step on. It never removes a shim and never shadows a directory placed ahead of the shims. An interpreter that `setup-node` or `setup-python` puts first on `PATH` is not shimmed, so a later `shell: node` or `shell: python` step runs with act's terminal and may differ from GitHub in terminal-dependent output.
- **`export-ignore` is not honoured.** A run's checkout is the whole commit, fetched and packed in process, which is what `actions/checkout` gives. The earlier path used `git archive`, which honours `export-ignore` in `.gitattributes`, so files a repo marks that way are now present where they were absent before. If a workflow relied on them being absent, it needs an explicit step.
- **Job splitting is configuration, not workflow syntax.** A heavy job is split across sandboxes by an operator rule (`splits`), never by anything in the repository, so a pull request cannot change it. See [Splitting a job across sandboxes](#splitting-a-job-across-sandboxes). A job with `strategy.matrix` is not split, and a step a rule names that was renamed runs in every shard.
- **Pull requests run the head commit, not the merge commit,** as described under [Pull request events](#pull-request-events).
- **`schedule` and `workflow_dispatch` are not ingested yet,** and reusable workflows are not yet verified (see the table above).

## Runner image toolset

GitHub's `ubuntu-latest` image comes with a large preinstalled toolset, and workflows assume it. Turntable's sandbox is a smaller image, built from `images/runner/Dockerfile`: the pinned `node:22-bookworm` base plus PowerShell 7 (pinned by version and checksum), `jq`, `rsync`, `zip` and `unzip`. A step that needs a tool the image lacks fails with exit 127, and the log says `<tool> is not available on this image` so it is not a bare "command not found". A tool the image lacks is simply absent, as on a runner without it: `command -v pwsh` fails, so a workflow's own probe (`if ! command -v pwsh; then echo ::notice::skipped; exit 0; fi`) skips and succeeds. Turntable puts a shim on `PATH` only for the interpreters that exist (it uses them to keep steps off a terminal), never for one that does not. Install the tool in a step if egress allows it, or use your own image.
